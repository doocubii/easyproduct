# easyproduct-backend

> 이미 만들어진 기획 문서 세트(기획서·화면구조(IA)·데이터 모델·정책서·화면 설계서)를 근거로, 그 서비스를 실제로 떠받칠 **백엔드 시스템을 설계**해 주는 스킬입니다. 산출물은 **백엔드 아키텍처 · 저장 설계 · 논리 스키마 · 인터페이스 계약** 네 문서이며, 이 중 저장 설계·논리 스키마·인터페이스 계약은 그 영역의 **SSOT(결정이 사는 곳)**가 됩니다.

[easyproduct 스킬 세트](../../README.md)의 일부입니다.

## 무엇을 하나

- 문서 세트를 읽어 **아홉 단계**(재료 추출 → 아키텍처 골격 → 저장 설계 → 인증·인가 → 논리 스키마 → 인터페이스 계약 → 비동기·외부 연동 → 비기능 → 잇고 점검)로 백엔드 설계를 만듭니다.
- **인터페이스 설계** — 요구를 모아 **전송 방식**(REST·gRPC·GraphQL·WebSocket·메시지 큐)과 그에 걸맞은 규격을 **확정**합니다. 요구의 출처는 여러 갈래입니다: 화면 설계서의 동작(`data.io` 중 `target`이 서버인 것) · 프로젝트가 가진 요청서 문서 · **화면이 없는 운영 요구**(배치·웹훅·정산) · 정책이 요구하는 일. 근거(`basis`)는 여러 개일 수 있고 **근거 0인 인터페이스는 만들지 않습니다.** 요구가 사라지지 않았는지 **양방향으로** 점검합니다.
- **프로젝트가 이미 요청서 문서를 갖고 있어도 우리 형식으로 이관하라고 하지 않습니다** — 그 형식은 프로젝트 것이고, `basis`의 `api-request` 갈래로 그대로 받습니다.
- **DB 설계 — 두 층으로** 냅니다. **저장 설계**는 데이터 모델의 그룹 하나하나를 저장소에 배치하고(관계형·문서형·키-값·벡터·객체·검색·브로커 중 **무엇을 왜 나누는지**, 그릇·키·인덱스·멀티테넌트 격리·보존), **논리 스키마**는 그 그릇 안을 정합니다(테이블·컬럼·논리 타입·**열거값 집합**·참조 관계와 삭제 동작·개념과 갈라진 지점과 이유·파생 ERD).
- **인증 방식** — 자격 증명을 어떤 형태로 두는지, 로그인 상태를 무엇으로 유지하는지, 권한을 어디서 판정하는지. 요구가 "로그인 상태가 필요하다" 정도로만 남긴 자리를 여기서 확정합니다.
- 비동기 처리, 밖에 기대는 지점과 **그것이 죽었을 때의 처리**, 비기능 요건(성능·가용성·관측·보안)도 함께 정합니다.
- 각 문서에 **태그된 JSON 블록**을 넣어 소프트웨어가 바로 읽고 점검하게 합니다. **산문이 원본(SSOT), JSON은 미러**라 산문을 고치면 블록을 다시 생성합니다(손으로 고치지 않음).

## 무엇을 하지 않나

- **언어·프레임워크를 특정하지 않습니다.** 저장소도 **종류**까지만 정하고 **제품**은 후보로만 남깁니다. 설계는 "무엇을 만족해야 하는가"이지 "무엇으로 만드는가"가 아닙니다.
- **데이터의 뜻·필드 구성을 정하지 않습니다** — 데이터 모델 소관입니다. 이 스킬은 그것을 **배치**할 뿐입니다.
- **제품 규칙(권한·보존·금지)을 만들지 않습니다** — 정책서 소관입니다. 근거가 없으면 `[확인 필요]`로 남깁니다.
- **화면·기능을 늘리지 않습니다** — IA·화면 설계 소관입니다.
- 요금·법률·조달 값처럼 문서에도 없고 설계로도 못 정하는 것은 **지어내지 않고** 소관과 함께 남깁니다.

## 언제 쓰나

- "백엔드 설계해줘", "서버 설계", "API 설계", "DB 설계", "인증 어떻게 할지", "REST로 할지 gRPC로 할지"를 문서로 정리하려 할 때.
- 기획서·IA·데이터 모델은 있는데 설계서의 "아직 안 정한 것"에 **백엔드 스택·저장 방식·인증 인프라가 `[확인 필요]`로 남아 있을 때.**
- 화면의 동작이나 프로젝트 요청서, 또는 **화면이 없는 운영 요구**를 **실제 인터페이스 계약으로 확정**해야 할 때.
- spec-kit(SDD)으로 백엔드 개발에 착수하기 전, 그 근거가 될 설계 문서가 필요할 때.
- 이미 만든 백엔드 설계에 인터페이스·저장소·인증 모드를 추가·수정하거나 찾아볼 때.

## 산출물

| 문서 | 기본 경로 | 무엇이 사나 |
|---|---|---|
| 백엔드 아키텍처 |  `ssot/backend/backend-architecture.md` | 시스템 구성·경계 · **인증 방식과 모드 등기부** · 외부 연동과 실패 처리 · 횡단 규약 · 비기능 |
| 저장 설계 |  `ssot/backend/backend-storage.md` | 저장소 목록·그룹 배치·키·인덱스·격리·보존 — **저장 배치의 SSOT** |
| 논리 스키마 |  `ssot/backend/backend-schema.md` | 테이블·컬럼·논리 타입·**열거값**·참조와 삭제 동작·파생 ERD — **논리 스키마의 SSOT** |
| 인터페이스 계약 |  `ssot/backend/backend-interface.md` | 인터페이스 전부(경로·method·인증·입출력·오류·멱등성) — **인터페이스 계약의 SSOT** |

- 스키마 네 개(`backend-architecture.v1` · `backend-storage.v1` · `backend-schema.v1` · `backend-interface.v1`)를 산출물 옆 `schemas/`에 복사합니다.
- 인터페이스가 많아지면 데이터 모델과 같은 방식(`machine.includes`)으로 인터페이스 계약을 도메인별로 나누고, 부분 파일은 `interfaces/` 하위 폴더에 모읍니다 — 위층에 네 산출물의 구분이 남아야 읽힙니다.
  (`apis/`가 아닌 이유: 이 계약은 REST 전용이 아닙니다. 이름은 **관례일 뿐 계약이 아니라서**, 이미 다른
  이름을 쓰는 프로젝트는 그대로 두면 됩니다 — 부분 파일을 찾는 정본은 `machine.includes`입니다.)

## 다른 문서와의 관계 (누가 무엇의 SSOT인가)

| 무엇 | SSOT |
|---|---|
| 데이터의 **뜻·필드 구성** | 데이터 모델 `data-model.md` |
| 데이터가 **어디에 놓이나**(배치·인덱스·격리) | 저장 설계 `backend-storage.md` (이 스킬) |
| 데이터가 **어떤 모양으로 놓이나**(테이블·컬럼·열거값) | 논리 스키마 `backend-schema.md` (이 스킬) |
| 프론트가 **무엇을 보내고 받아야 하나** | 화면 설계서의 동작 `data.io`(+ 프로젝트가 따로 요청서를 가졌다면 그 문서) |
| **어떤 주소로 어떻게 주고받나** | 인터페이스 계약 `backend-interface.md` (이 스킬) |
| 제품 규칙 | 정책서 `policy.md` |
| 화면·기능의 범위 | 화면·기능 구조 `ia.md` · 화면 설계서 |

> 데이터는 **개념(데이터 모델) → 배치·논리(저장 설계·논리 스키마) → 물리(마이그레이션 코드)** 세 층으로 갈립니다. 이 스킬이 채우는 것은 가운데 층이며, 개념 층을 덮어쓰지 않고 물리 층(실제 타입 이름·문자셋·인덱스 구현)은 코드에 맡깁니다.

## 단독 실행 vs 세트

- 기본은 **단독 동작**입니다. 문서 세트가 다 갖춰지지 않아도 없는 것을 밝히고 진행합니다.
- 단, **데이터 모델이 없으면 저장 설계를 하지 않습니다** — 데이터의 뜻이 정해지지 않았는데 저장 위치를 정하는 것은 순서가 뒤집힌 것입니다.
- 백엔드 설계 문서를 받으면 그것을 기준선(SSOT)으로 삼아 조회·수정·추가를 이어가고, 새로 생성하지 않습니다. 기획 문서를 함께 받아도 **설계 문서가 우선**입니다.
- 읽기(read)는 문서를 직접 읽으면 되고, 쓰기·판정(새 인터페이스·저장소 분리 결정·커버리지 점검)이 필요할 때만 이 스킬을 부릅니다.

## 구성 파일

- `SKILL.md` — 스킬 본문(여덟 단계 생성 절차, 수정·조회, 커버리지 점검, 명명·크로스참조 규칙, 정합성 점검).
- `assets/backend-architecture-template.md` · `assets/backend-storage-template.md` · `assets/backend-schema-template.md` · `assets/backend-interface-template.md` — 네 문서의 구조. frontmatter·SSOT 문구·기계 블록 자리 포함.
- `references/storage-selection-guide.md` — 저장소를 **언제 나누고 언제 나누지 않는지**, 종류별 적합·부적합, 격리 방식의 대가, 인덱스·보존 원칙.
- `references/auth-patterns.md` — 인증 상태 유지 방식의 갈림길과 대가, 망 분리 환경 제약, 인가 모드 설계, 오류 구분.
- `references/logical-schema-guide.md` — 개념을 물리로 옮길 때의 갈림길: 논리 타입, 제품 결정처럼 보이지만 논리로 끌어올려야 하는 것(대소문자 유일성 등), 식별자 전략, 개념 하나가 테이블 여럿이 되는 경우, 참조 무결성·삭제 동작, 소프트 삭제와 파기, 열거값에서 "등" 없애기.
- `references/interface-conventions.md` — 전송 방식·응답 봉투·오류 코드·페이징·멱등성·버전·시간/숫자/파일 규약의 후보와 고르는 기준.
- `schemas/*.v1.schema.json` — 세 기계 블록의 검증 계약(고정 자산, 산출물 옆으로 복사).

## 세트 안에서의 위치

- 기획서·IA·데이터 모델·정책서(·화면 설계서)가 나온 **뒤**, spec-kit(SDD)으로 개발에 들어가기 **전** 단계입니다. 데이터 모델과 화면의 동작이 있어야 성립하므로 파이프라인 뒷부분입니다.
- 설계서(`design-doc`)가 `[확인 필요]`로 남긴 백엔드 빈칸 — 스택·저장 방식·인증 인프라·결제 연동·성능 목표 — 을 실제로 채우는 자리이며, 채운 뒤에는 설계서의 해당 항목을 이 문서들로 가리키게 back-fill 하는 것이 자연스럽습니다.
- 산출된 네 문서는 spec-kit 인계 안내문의 **SSOT 구분표**에 "백엔드 인터페이스 계약 / 저장 배치 / 시스템 구성의 SSOT"로 들어갑니다.
