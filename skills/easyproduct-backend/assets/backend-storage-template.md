# 저장 설계: [서비스 이름]

> 이 문서는 데이터가 **어디에 · 어떤 모양으로 · 어떻게 갈라져 · 무엇으로 빨리 찾아지는지**에 관해 다른
> 어떤 문서보다 우선하는 기준(SSOT)이다. 다만 **데이터의 뜻과 필드 구성은 데이터 모델 문서가 기준**이다 —
> 이 문서는 그것을 **배치**할 뿐 다시 정의하지 않는다. 필드가 모자라면 여기서 만들지 말고 데이터 모델에서 만든다.
>
> **저장소의 '종류'는 이 문서가 정하고, '제품'(어느 DB 제품을 쓸지)은 정하지 않는다.** 후보만 적는다 —
> 제품을 여기서 못 박으면 제품이 바뀔 때 "설계가 틀렸다"와 "제품을 바꿨다"가 구분되지 않는다.
>
> 이 문서를 고칠 때는 아래를 지킨다:
> - `BESTORE.*` ID는 한 번 부여하면 바꾸지 않는다.
> - 산문을 고치면 아래 JSON 블록을 **산문 기준으로 다시 생성**한다(JSON을 손으로 고치지 않는다).
> - **인덱스는 실제 조회에서 유도한 것만 넣고 `왜`를 함께 적는다.** 추측으로 깔지 않는다.
> - 여러 조직·계정의 데이터가 섞이는 그릇에는 **격리 방식과 그 한계**를 반드시 적는다.
>
> **함께 보는 문서**: 데이터 모델 `data-model.md`(데이터의 뜻) · 인터페이스 계약 `backend-interface.md`(조회 패턴의 근거) ·
> 아키텍처 `backend-architecture.md`(어느 조각이 어느 저장소를 소유하나) · 정책서 `policy.md`(보존·파기)

## 기계용 블록

아래 블록은 위 산문의 **미러**다. 산문이 원본이며, 산문을 고치면 이 블록을 다시 생성한다.
**손으로 고치지 않는다.** **산문에 적은 저장소·그릇·인덱스를 빠짐없이 담는다.**

```json backend.stores
{
  "stores": [
    {
      "id": "BESTORE.[이름]",
      "kind": "relational",
      "purpose": "[왜 따로 있나]",
      "productCandidates": ["[후보]"],
      "durability": "persistent",
      "isolation": {
        "strategy": "shared-key",
        "key": "[기준 값]",
        "desc": "[무엇을 보장하고 무엇은 아닌지]"
      },
      "holds": [
        {
          "container": "[그릇 이름]",
          "desc": "[무엇을 담나]",
          "group": "[데이터 모델 그룹]",
          "key": "[키]",
          "indexes": [
            { "fields": ["[필드]"], "unique": false, "why": "[근거 — BEITF.* / POL.*]" }
          ],
          "retention": "[보존]",
          "embedded": false
        }
      ],
      "notes": "[트랜잭션·일관성·백업 제약]"
    }
  ],
  "unmapped": []
}
```

### 이 블록으로 소프트웨어가 자동 점검할 수 있는 것

- **ID 형식** — `BESTORE.*`가 규칙대로인지, 전역 유일한지.
- **그룹 배치 커버리지** — 데이터 모델의 모든 그룹이 어느 `holds[].group`에 있는지(빠진 그룹 = 저장할
  곳 없는 데이터). `unmapped`가 비어 있는지.
- **죽은 링크** — `holds[].group`이 데이터 모델에 실재하는지.
- **빠진 내용** — 그릇에 뜻(`desc`)이, 인덱스에 근거(`why`)가, 테넌트 데이터를 담는 저장소에 격리가
  비어 있지 않은지.

이 배치가 타당한지(이 저장소 분리가 필요한가·이 인덱스가 정말 그 조회를 살리나)는 소프트웨어가 판단할 수
없다 — 사람 또는 LLM의 풀 리뷰 몫이다.
