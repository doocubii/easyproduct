# SDD 강제 하네스 — 설치·배선

## 목적

spec-kit 프로젝트에서 **"이 코드가 승인된 spec에서 파생됐는가(프로세스 출처)"를 검사하는 층이 없다.**
린트·타입·테스트·CI는 **코드 품질**만 보고, `verify`는 spec-first든 code-first든 똑같이 통과한다.
이 스킬은 그 빈 층을 **정책 파일 + 무의존 검사기 + 훅/verify/CI 배선**으로 채운다.

**발동**: 대상 프로젝트에 `.specify/`가 있을 때. 없으면 **"spec-kit init 먼저"**를 안내하고 **중단**한다
(가드는 spec-kit 위에서만 의미가 있다).

## 이 스킬이 하지 않는 것 (경계)

- **제품의 SSOT를 저작하지 않는다.** 기획서·`spec.md`·`plan.md`·`tasks.md`를 대신 써 주지 않는다.
  이 스킬이 만드는 문서는 **하네스 운영 문서**뿐이다 — 정책 파일, 규약 README, 핀·리뷰 기록 **템플릿**
  (템플릿의 내용을 채우는 것도 사용자·에이전트의 몫이다).
- **다른 easyproduct 스킬을 호출하지 않고, easyproduct 문서를 전제하지 않는다.** 있으면 어댑터로 활용할 뿐.
- **규범을 발명하지 않는다.** 헌법·CLAUDE.md·AGENTS.md에 적힌 SDD 규범을 **실행 게이트로 승격**할 뿐이다.
  규범 자체가 없으면 "보강 권고"를 리포트에 남기고, 문구를 대신 써 넣지 않는다.
- **의미 판정을 하지 않는다.** "spec이 기획서와 뜻이 맞나"는 사람/LLM 몫이고, 이 하네스는 **그 리뷰가
  생략되지 못하게** 기록을 요구한다(규칙 ⑦).
- **비전문가 저작 흐름에 끼어들지 않는다.** 산출물·용어가 전부 개발자용이다.

## 막으려는 실패 3종 → 7규칙 3축

문서 층: **1) 상위 문서**(기획서·SSOT·설정·헌법) → **2) spec-kit 문서**(`specs/<slug>/`) → **3) 소스코드**.

| 실패 | 축 | 규칙 |
|---|---|---|
| **C1** SDD 없이 소스부터 고침 | 코드 층 | **① 출처** 관장 파일마다 `@sdd <slug>` 태그 · **② 완결** 슬라이스에 필수 산출물+핀 파일 · **③ 결합** 코드가 바뀌면 그 슬라이스도 바뀌어야 |
| **C2** 상위 문서 변경이 흐름을 못 탐 | 전파 층 | **⑥ 역결합** 상위 문서만 바뀌고 슬라이스가 안 바뀌면 위반 · **④ 신선도** 슬라이스가 핀한 상위의 `version`+`contentHash`가 현재와 일치해야 |
| **C3** 상위와 충돌하는 spec 수정 | 내용 층 | **⑤ 근거** spec/plan이 참조한 앵커가 상위 등기부에 실재 + 근거 0인 요구 금지 · **⑦ 리뷰 기록** spec/plan을 고쳤으면 상위 대조 기록을 남겨야 |

**축이 셋인 이유**: 코드 층만 조이면 나머지 두 축으로 SDD가 그대로 새어 나간다. C2는 spec-kit 생태계
전체에서 아무도 안 보는 빈칸이고(`references/ecosystem-overlap.md`), 이 하네스의 핵심 가치다.

## 절차

### Step 0 — 조사(audit)를 먼저, 제대로

설치·배선 전에 **9항목**을 각각 확인해 리포트를 내고, 사용자에게 보여주고 확정받은 뒤 진행한다.
얕게 감지하지 않는다.

| # | 조사 질문 | 결과가 정하는 것 |
|---|---|---|
| 1 | **spec-kit이 있나?** (`.specify/`·`constitution.md`·`specs/`의 `NNN-kebab` 슬라이스) | 없으면 **중단**하고 init 안내 |
| 2 | **스택·프레임워크는?** (매니페스트 + **의존성 스캔**) | `governedGlobs`·주석 문법·allowlist·통합 지점 (`references/stack-adapters.md`) |
| 3 | **상위 문서 층이 어디에 어떤 형식으로 있나?** (frontmatter `version:`+기계 블록 / 버전 라인·헤딩만 / 표식 없음) | **문서 어댑터**(`easyproduct` vs `generic`)와 `upstreamDocs.globs` |
| 4 | **SDD 규범이 실제로 적혀 있나?** (헌법·CLAUDE.md·AGENTS.md 텍스트 확인) | 없거나 얇으면 **보강 권고**를 리포트에(대신 써 주지 않는다) |
| 5 | **기존 게이트는 어디에?** (`verify`·Makefile·pytest·pre-commit·CI·에디터 훅) | 새 파이프라인을 만들지 말고 **거기에 얹는다** |
| 6 | **spec-kit 확장이 이미 깔려 있나?** (`.specify/extensions.yml`·`.speckit-ci.yml`·Gates `policy.json`·`<!-- blueprint:` 마커) | **중복 회피** — 겹치는 규칙은 끄고 위임한다 (`references/ecosystem-overlap.md`) |
| 7 | **관장 범위에 사각이 없나?** (어느 glob에도 안 걸리는 소스 파일 수) | glob 확장 또는 `unmatchedNewFiles: warn` |
| 8 | **이 하네스가 이미 깔려 있나?** (정책 완결성·검사기 버전·배선이 실제로 연결됐나) | 미설치=신규 / 오설정·구버전=갱신 / 정상="할 것 없음" 보고 |
| 9 | **저장소 루트가 spec-kit 루트와 다른가?** (`.specify/`가 하위 폴더에 있나, 트랙이 여러 개인가) | 다르면 **`references/monorepo.md`를 따른다** — 모든 경로에 트랙 접두, 형제 트랙을 allowlist로 제외, `upstreamDocs.globs`를 내 트랙 근거로 좁힘, `mainBranch`를 트랙 머지 타깃으로. 트랙마다 **정책 하나씩** |

### Step 1 — 정책 확정 (`sdd-policy.json`)

조사 리포트로 **초안을 만들어 제안하고 확인받아 확정**한다. 프로젝트마다 다른 것은 이 파일뿐이고,
검사기·훅은 이 파일만 읽는다(프로젝트 이름을 로직에 박지 않는다).
템플릿: `assets/sdd-policy.template.json` — 필드 의미는 그 파일의 주석과 `references/checker-pseudocode.md`.

- Step 0-3의 어댑터·상위 문서 글롭·앵커 추출 규칙을 여기에 박는다.
- Step 0-6의 중복 판정을 `delegated`·`severity`에 반영한다(예: CI Guard가 있으면 `completeness: "off"`).
- **브라운필드는 `mode: "warn"`으로 시작**한다(아래 Step 5).

### Step 2 — 검사기 설치

- **참조 구현 2종이 동봉돼 있다** — 대상 런타임에 맞는 것을 **재생성하지 말고 복사**한다(시간·토큰 절약):
  - `scripts/sdd-check.mjs` — 무의존 Node(ESM)
  - `scripts/sdd_check.py` — 무의존 Python 3.8+(표준 라이브러리만)
  - 둘은 **같은 정책·같은 저장소에서 동일한 위반 목록·종료코드**를 낸다(`--json`으로 대조 검증됨).
- **그 외 런타임**(Go·Rust·JVM…)은 **수도코드가 정본이므로** `references/checker-pseudocode.md`의
  알고리즘대로 그 언어 구현을 생성한다. 이때 동봉된 두 구현을 참고 예시로 쓴다.

어느 언어든 지켜야 할 것:

- **무의존 단일 파일**, 정책 파일만 읽는다.
- 종료코드: `--full`은 **0=통과 / 1=block 위반 / 2=설정 오류**, `--changed`는 **0=통과 / 2=위반**(훅이 주입하려면 2여야 한다). `--json` 출력 지원.
- 모드: `--changed <files>`(훅용, 빠르게) / `--full`(verify·CI용, 전부).
- 리포트 머리말에 **어떤 어댑터를 썼고 어떤 규칙을 껐는지·누구에게 위임했는지** 명시한다.

**배치**: 대상 프로젝트에 **이미 하네스 폴더가 있으면 그 아래 전용 하위 폴더로 모은다**
(예: 기존 `harness/`가 있으면 `harness/sdd/`). 검사기를 부르는 스크립트에서 `dirname "$0"` 기반 상대
경로로 `cd`할 때는 **폴더 깊이가 바뀐 만큼 경로도 바뀐다** — 재편 후 반드시 한 번 실행해 확인한다.

### Step 3 — 게이트 배선 (4층)

Step 0-5·0-6에서 찾은 지점에 **얹는다**. 이미 있는 하네스를 밀어내지 않는다.

| 층 | 무엇 | 성격 |
|---|---|---|
| ⓪ 규범 상주 | (Claude Code면) `SessionStart` 훅 — "이 프로젝트엔 SDD 게이트가 있다 + 열린 슬라이스" 주입 | 예방 |
| ① 빠른 피드백 | `PostToolUse` 훅에 `--changed`(위반 시 `exit 2`로 에이전트에 주입). Claude Code가 아니면 `pre-commit` | 로컬·끌 수 있음 |
| ② 완료 게이트 | `verify`(또는 등가 스크립트)에 `--full` | 로컬 게이트 |
| ③ **실제 강제** | **CI 잡에 `--full`** — 실패 = 파이프라인 실패 = 머지 차단 | **차단** |

- **필수 규칙은 반드시 CI에도 건다.** 로컬 훅은 편의일 뿐이고, 에이전트는 훅 배선 자체를 고칠 수 있다.
- **CI는 전체 히스토리를 받아야 한다.** ③⑥이 `merge-base`를 쓰는데 CI 기본 얕은 클론이면 실패해
  HEAD~1로 후퇴한다(리포트에 skipped로 뜬다). **GitLab은 `GIT_DEPTH: 0`, GitHub Actions는
  `actions/checkout` 의 `fetch-depth: 0`**을 함께 넣는다.
- **`mode: "warn"`(브라운필드)은 verify·CI 층에만 적용된다 — 훅 층은 계속 살아 있다.** 훅은 방금 편집한
  파일만 보므로 warn 기간에도 `exit 2`로 주입한다(끄려면 `hooks.injectOnWarn: false`). 이게 없으면
  도입 기간 내내 ①층이 조용히 죽는다.
- **사전 차단(`PreToolUse` deny)은 기본 off.** 정당한 작업까지 물리는 비용이 커서 기본값으로 두지 않는다.
  강하게 막아야 하는 프로젝트만 `hooks.preToolUseDeny: true`로 옵트인.
- **Gates 확장이 이미 있으면** 훅을 새로 깔지 말고 그 `policy.json`의 tool gate로 검사기를 등록한다.
  **CI Guard가 있으면** CI 잡을 새로 만들지 말고 같은 잡에 붙인다(리포트 창구를 하나로).

### Step 4 — 프로젝트 README 생성

`assets/project-readme.template.md`를 그 스택에 맞게 채워 대상 프로젝트에 남긴다:
태그 규약(`@sdd <slug>`)·핀 선언법(이중 핀)·⑦ 리뷰 기록 쓰는 법·예외 선언법·상위 변경 시 재검토 절차.

### Step 5 — 브라운필드 도입 (기존 코드가 많을 때)

무태그 코드가 많으면 켜는 순간 전부 위반이 된다. **반드시 `mode: "warn"`(완료 게이트에서 경고, exit 0)으로
시작**해 정리한 뒤 `mode: "block"`으로 전환한다. 규칙별 기본 severity는 **①②③⑥ = `block` · ⑤⑦ = `warn`**이다.

**순서가 중요하다 — 핀 먼저, 태그 나중.**

| 단계 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| **1** | **슬라이스마다 `sources.json` 핀을 채운다**(②의 핀 검사 + ④⑥ 가동) | **핀이 없으면 ④가 침묵**해서, 이 하네스의 핵심 가치인 **C2(상위 변경이 흐름을 안 탐)가 계속 0으로 남는다.** 비용은 슬라이스당 파일 하나뿐인데 가장 크게 새는 구멍을 바로 막는다 |
| **2** | **관장 파일에 `@sdd` 태그를 백필**한다(①③ 가동) | 파일 수만큼 손이 가지만 기계적이다. 라우트·화면은 슬라이스와 거의 1:1이라 유추가 쉽다 |
| **3** | **⑤⑦을 튜닝 후 `block`으로 승격**, 전역 `mode`도 `block` | 등기부·기록 관습이 자리 잡은 뒤에 올린다 |

> **팀은 기계적으로 쉬운 태그(①)부터 손대기 마련이다.** 그러면 몇 주 동안 ④가 침묵한 채 상위 문서 변경이
> 계속 새어 나간다. 조사(Step 0)에서 히스토리를 세어 보라 — 상위 문서만 바뀐 커밋이 얼마나 되는지가
> 이 순서의 근거다(실제 프로젝트 실측: 상위 문서 변경 커밋의 **75%가 슬라이스 무동반**이었다).

**태그가 0건이어도 ②④는 돈다.** 대상 슬라이스 범위는 `specsDir`의 선언 슬라이스 전부가 기본이라
(`sliceScope`), 태그 백필 전에도 핀 검사·신선도가 작동한다 — 그래서 위 순서가 성립한다.

### Step 6 — 재실행·헬스체크 (멱등)

이미 깔린 프로젝트에서 다시 부르면 Step 0의 판정으로 **정책·검사기·배선만 갱신**한다(중복 설치 금지).
확장이 나중에 깔렸으면 그때 중복 규칙을 내린다. 구버전 정책은 새 필드를 채우되 **신규 규칙은 warn으로 먼저** 켠다.

## 기존 생태계에 위임하는 것 (중복 금지)

**남이 이미 하는 검사는 하지 않는다.** 판단 근거와 조사 결과는 `references/ecosystem-overlap.md`에 있다.

- **② 완결 → CI Guard**가 있으면 아티팩트 존재·완결성은 그쪽에 맡기고 `off`. 단 **핀 파일 검사만은 남긴다**(④의 전제).
- **⑦의 리뷰 실행 → `/speckit.analyze`**(있으면 `/speckit.checklist`도). 우리는 리뷰를 발명하지 않고,
  그 출력을 기록에 붙이게 안내한 뒤 **기록의 존재·최신성만** 검사한다.
- **배선 → Gates**의 3경계를 재사용한다(위 Step 3).
- 다만 **어느 확장에도 의존하지 않는다.** `delegated`가 전부 false여도 하네스는 완결 동작한다.

## 한계 — 설치할 때 사용자에게 반드시 알린다

7규칙은 **의례·공존을 강제**하지 **인과적 파생·의미 정합을 검증하지 않는다.**

- 우회 경로가 실재한다: 태그만 붙이기(①) · 슬라이스 폴더 no-op 편집(③⑥) · 핀 숫자만 갱신(④) ·
  리뷰 기록을 형식만 채우기(⑦). ⑤는 앵커가 **실재**하는지만 보지 **옳게 해석했는지**는 못 본다.
- **기계 통과 ≠ 검증 완료.** 이 하네스는 프로세스 생략을 **가시화·유료화**하는 forcing function이며,
  우회하면 그 흔적이 **커밋 히스토리와 리뷰에 남는다**는 것이 실제 효용이다.
- **에이전트가 훅 배선 자체를 고칠 수 있다.** 그래서 **CI가 최종 backstop**이고, 로컬 층만 깔고 끝내지 않는다.
- C3의 진짜 충돌 판정은 ⑦이 강제한 **사람/LLM 리뷰**의 몫이다.
