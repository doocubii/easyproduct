# 파장 지도 — 상위 결정이 바뀌면 무엇이 따라와야 하나

> **왜 필요한가**: 확정된 상위 결정이 바뀔 때(예: "계정 2개" → "계정 1개 + 워크스페이스 전환"),
> 무엇이 영향을 받는지 판정하는 절차가 없으면 실행자는 **자기가 아는 방법(검색)으로 채운다.**
> 검색은 유한 목록을 주므로 "다 처리했다"는 완료 신호가 나지만, **문서 구조에서 예측된 것이 아니라**
> grep이 발견한 것뿐이라 산문에만 있는 파장(참조 ID가 없는 것)은 통째로 빠진다.
>
> **정본은 `assets/propagation-map.json`이다.** 이 문서는 그 값의 근거와 읽는 법을 설명한다.

## 지도의 위치와 이유 (프로젝트가 아니라 스킬이 갖는다)

파생 관계는 **문서 종류 사이의 관계**다 — "화면 설계서는 IA·디자인 컨셉·데이터 모델에서 파생된다"는
**모든 프로젝트에서 같다.** 그래서 프로젝트 매니페스트마다 손으로 적지 않고 **스킬 자산 한 곳**에 둔다.

- 프로젝트는 추가 저작 부담이 **0**이다(매니페스트를 손대지 않는다).
- 지도가 프로젝트마다 어긋날 일이 없다. 손으로 유지되는 중복 데이터는 틀어지면 **거짓말하는 지도**가 된다
  (빈 껍데기보다 나쁘다 — 있는데 틀린 것).
- 갱신 지점이 하나다. 단계 간 인계가 바뀌면 `skill-handoff-guide.md`와 이 지도를 함께 고친다.

**예외만 프로젝트에 적는다.** 특정 문서가 표준과 다른 상류를 가지면 `00-index.md`의 매니페스트 항목에
`derivesFrom`(선택 필드)으로 덮어쓴다. 그때만 프로젝트가 값을 갖는다.

## 지도 (요약)

| 하류 문서 | 상류(derivesFrom) | 근거 |
|---|---|---|
| `design-doc`(설계서) | `plan` | Stage 1 Phase A→B |
| `ia` | `plan` · `design-doc` | handoff §2(정체성·유형·핵심기능·규칙·금지) |
| `data-model` | `plan` · `ia` | handoff §7(정보 덩어리 → 그룹) |
| `design-concept` | `plan` | handoff §3 |
| `policy` | `plan` · `ia` · `data-model` | 규칙의 원본이 기획, 적용 지점이 화면·데이터 |
| `terms-privacy` | `policy` · `plan` · `data-model` | 약관이 계정·결제 정의를 **산문으로** 서술 |
| `screen-design` | `ia` · `design-concept` · `data-model` · `policy` · `plan` | handoff §9-3.8-A 재료표 그대로 |
| `screen-design-index` | `ia` · `screen-design` | 목록·순서가 IA를 따른다 |
| `ui-components` | `screen-design` · `design-concept` | 화면 설계에서 공통 컴포넌트가 자란다 |
| `scenario` | `ia` · `policy` · `data-model` · `screen-design` | 시나리오는 링크-온리 파생물 |
| `doc-bundle-index` | (없음) | 색인은 파생물이 아니라 목록 |

## 이 지도가 잡으라고 만들어진 것 (실제 사고)

기계 점검(`check-docs.mjs`)이 **원리적으로 못 잡는** 파장이 있다. 셋 다 실제로 뚫렸다.

1. **산문 정의의 어긋남** — IA는 "N개 워크스페이스"로 고쳤는데 화면 설계서 GNB 정의가 `(개인 ↔ 조직)`
   2항 표현 그대로. **어떤 ID도 참조하지 않는 산문**이라 죽은 링크가 아니다.
2. **없는 파라미터** — 화면 전역 표준이 "GNB에 활성 워크스페이스 항상 표시"를 요구하는데
   `ui-components`의 `UI.nav.gnb`에 그 값을 받을 파라미터가 **아예 없다.** 없는 것은 죽은 링크가 아니다.
3. **통째로 잊힌 문서** — 약관이 계정 정의를 서술하는데 목록에서 빠져 한 번 누락됐다.

→ 셋 다 **"상류가 바뀌면 이 하류도 본다"**는 목록이 있어야만 시야에 들어온다.

## 쓰는 법 (변경 전파 모드)

1. **진원지**를 정한다 — 바뀐 결정이 **사는** 문서(`doc_type`으로 판정, `SKILL.md` 변경 전파 모드 참조).
   증상이 발견된 문서에서 시작하지 않는다.
2. 지도를 **정방향으로 닫아** 하류 목록을 만든다(진원지를 상류로 갖는 문서 → 그 문서를 상류로 갖는 문서 → …).
3. 그 목록이 **작업 범위**다. 파이프라인 순서대로 내려가며 각 단계에서 두 질문에 답한다:
   - 상류의 이 변경이 **이 문서에 무엇을 낳는가?**
   - 이 문서에 **새로 생긴 요구**가 있는가? 있다면 그것이 **다음 문서에 무엇을 낳는가?**
     *(두 번째 질문이 위 사고 2번을 잡는 질문이다 — 화면에 생긴 요구가 컴포넌트 파라미터를 낳는다.)*
4. 목록 밖 문서를 고치게 되면 **기록하고 지도를 의심한다**(§변경 전파 모드의 범위 증가 규칙).

## 한계 (정직하게)

- 이 지도는 **문서 종류 단위**다. "IA의 어느 절이 어느 화면 파일에 닿는가"까지는 모른다 — 그 좁히기는
  사람/LLM 몫이고, 지도는 **볼 문서를 빠뜨리지 않게** 하는 장치다.
- 파생 관계는 **역방향 참조가 아니다.** `check-docs.mjs`의 죽은 링크 검사(ID 참조)와 층이 다르다 —
  ID 참조는 "가리킨 것이 실재하나", 파장 지도는 "바뀐 것을 따라갔나"를 본다.
