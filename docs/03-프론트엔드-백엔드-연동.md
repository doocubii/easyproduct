# 프론트엔드 ↔ 백엔드 연동 — 화면의 동작이 어떻게 서버 계약이 되나

> **읽는 사람**: 프론트·백엔드 개발자와 그 에이전트. (0.8.0에서 추가)

## 층이 넷입니다

```
① 화면 설계서의 동작(data.io)      프론트 소유 · 전송 중립
        │  기계 추출
        ▼
② 인터페이스 요청서                프론트가 만들어 넘김 · 파생물
        │  전송 결정 · 묶기 판단
        ▼
③ 인터페이스 계약(backend-interface)  백엔드 소유 · SSOT
        │
        ▼
④ 구현                            계약을 따른다
```

각 층이 정하는 것이 다릅니다. **아래 층이 위 층을 뒤지지 않는 것**이 핵심입니다.

| 층 | 무엇을 정하나 | 무엇을 정하지 않나 |
|---|---|---|
| ① 화면 동작 | 무엇을 보내고 받나 · **누구와**(server/local/client) · 걸리는 규칙 · 행동 규약 | 경로·메서드·전송 방식 |
| ② 요청서 | ①을 모아 전달 · 희망 전송 | 확정된 것 아무것도 (파생물) |
| ③ 계약 | **전송 방식**과 그 규격 · 인증 · 오류 · 멱등 | 프레임워크·언어·저장소 제품 |
| ④ 구현 | 코드 | 계약을 바꾸지 않는다(바꿔야 하면 ③으로 돌아감) |

## ① 화면 동작 — `io[]`가 담는 것

```json
{ "id": "IO.order.create.submit",       // 다른 문서가 이 동작을 가리키는 안정적 이름
  "action": "예약하기",
  "target": "server",                    // server | local | client  (+ server.MAIN_SERVER 같은 한정자)
  "ui": "UI.button.primary",
  "sends": ["order.pickupSlot"],         // 데이터 모델 실재 변수만
  "receives": ["order.id"],
  "policies": ["POL.order.serviceArea"], // 이 동작에 걸리는 제품 규칙
  "semantics": "두 번 눌러도 주문은 하나만" }
```

## 요구는 세 갈래로만 옵니다

```
화면 안에서 일어난다        → 그 화면의 data.io
껍데기에서 일어난다          → 프레임의 data.io   (screendesign.frame — index 문서)
화면이 아예 없다(배치·웹훅)  → 백엔드 계약의 basis: ops + why 필수
```

**가운데가 비어 있던 동안 그 요구들은 양옆으로 흘러넘쳤습니다.** GNB·LNB·상단바에도 서버와 주고받는
일이 있는데(세션 조회·로그아웃·워크스페이스 전환) 어느 화면 것도 아니라 담을 자리가 없었습니다.
실측으로 요청서 96건에 **세션 조회가 없었고**, 로그아웃은 `IO.my.home.logout`으로 **마이페이지에
억지로 붙어** 있었습니다 — 마이페이지를 안 거치고 로그아웃하는 경로가 문서상 사라진 상태였죠.

프레임 동작은 요청서에 **`frame`·`appliesTo`와 함께** 실립니다. 백엔드가 이걸 개별 화면의 조회로
오해하면 **호출 빈도·캐시·세션 저장소를 잘못 잡습니다** — 화면 20개짜리 백오피스에서 세션 조회는
가장 많이 불리는 인터페이스니까요. `appliesTo`의 예외(대개 로그인 화면)도 함께 갑니다.

**`io`는 "누르는 것"만이 아닙니다.** 화면 산문의 두 절을 모두 담습니다.

| 산문 절 | `io` 항목 |
|---|---|
| **화면에 들어오면 일어나는 일** | 진입 로드 — `IO.<도메인>.<화면>.load` · `ui` 없음 · `sends: []` |
| **여기서 할 수 있는 일** | 사용자 동작 — 누르는 것, `ui`로 트리거 컴포넌트를 밝힘 |

진입 로드를 빠뜨리면 **그 화면은 요청서에 한 줄도 안 나가고**, 백엔드는 그 조회 인터페이스가 없는 줄 압니다.
실측으로 한 세트에서 화면 52개 중 15개가 그 상태였습니다 — 보여줄 데이터 244개를 선언해 놓고요.
그래서 점검기가 **"보여준다고 했는데 아무 동작도 가져오지 않는 데이터 n건"**을 상설로 집계합니다.

> `display`와 진입 로드의 `receives`는 크게 겹치지만 **뜻이 다릅니다.** `display`는 "보인다"(계산된 값·
> 앞 화면에서 넘어온 값·정적 문구 포함), `receives`는 "가져온다". **그 차집합이 위 점검의 근거**라 둘 다 남습니다.

**`target`이 가장 중요합니다.** `io`는 서버 통신 전용이 아닙니다 — **기기에 저장하는 것(local)**과
**화면 안 상태만 바꾸는 것(client)**도 동작이라 여기 담깁니다. 구분이 없으면 백엔드가
**로컬 임시저장이나 화면 이동에까지 엔드포인트를 지어냅니다.**

> 실제 사례: 로그인 화면의 동작 5개 중 서버와 통신하는 건 "로그인"뿐이고,
> "개인 가입 이동"·"비밀번호 찾기"·"약관 링크"는 전부 화면 이동이었습니다.

**누가 쓸 수 있는지는 `auth`에.** `target`이 서버면 **필수**입니다.

```json
{ "id": "IO.admin.product.list.toggleVisible", "target": "server",
  "auth": { "required": true, "roles": ["operator"] },
  "policies": ["POL.product.visibility"] }
```

- **`required`** — 로그인이 필요한가. **`roles`** — 어떤 역할이 쓰는가(제한이 없으면 생략).
- **방식은 적지 않습니다** — 토큰이냐 세션이냐는 백엔드가 정할 계약(`auth.mode`)이고, 여기는 요구입니다.
- **없는 것을 "인증 불필요"로 읽지 않습니다.** 실측으로 서버 동작 135건 중 82건이 권한 정보 없이
  백엔드로 나갔고 **그중 27건이 운영자 전용**이었습니다(청구 목록·상품 노출 토글). 기본값을 주면
  그것들이 공개 엔드포인트가 됩니다. 판단이 안 서면 지어내지 말고 `[확인 필요]`를 남기세요.

> **묶기 판단이 이걸 봅니다.** "권한이 다르면 묶지 마라"가 금지 신호 1번인데, 지금까지 그 재료가 요구에
> 없어 기계는 볼 수 없었습니다. 이제 **권한이 다르면 후보로 올리지 않고, 미분류는 자기들끼리도 안 묶습니다.**

**저장하지 않는 입력은 `transientSends`에.** 검색어·자동로그인 체크처럼 **보내지만 기억하지 않는 값**은
데이터 모델에 없는 게 정상입니다 — 데이터 모델은 **저장 설계의 유일한 입력**이라 넣으면 컬럼이 됩니다.
그렇다고 안 적으면 **검색 동작이 `sends: []`로 넘어가 백엔드가 "입력 없는 검색"을 요구로 받습니다.**

```json
{ "id": "IO.lawReview.lawSearch.search", "action": "검색", "target": "server",
  "sends": [],
  "transientSends": [ { "name": "keyword", "desc": "법령명·조문 검색어" } ],
  "receives": ["law.id", "law.name", "law.summary"] }
```

`{name, desc}`로 **뜻까지** 담습니다 — 등기부 대조를 안 받는 자리라 이름만 있으면 나중에 판단할 수 없고,
실재 변수를 여기 적으면 `sends` 제약을 우회하는 것이라 점검기가 잡습니다.
**`page`·`size`·정렬은 여기 적지 않습니다** — 커서냐 오프셋이냐는 백엔드가 정할 **계약**이지 요구가 아닙니다.

`policies`·`semantics`는 **산문에 이미 적혀 있는 것을 블록에도 담는 것**입니다. 안 담으면 백엔드가
오류의 근거·멱등·정렬·동기 여부를 정할 재료가 통째로 안 넘어갑니다(손실 미러).

## ② 인터페이스 요청서 — 기계가 뽑습니다

**화면 설계서와 같은 입자로 갈립니다 — 범위별 폴더, 도메인별 파일.**

```
screens/user/                        interface-requests/user/
├── screen-design-user-auth.md   →   ├── interface-request-user-auth.md
├── screen-design-user-order.md  →   ├── interface-request-user-order.md
└── screen-design-user-help.md   →   (서버 동작 0건이면 파일 없음)
```

```bash
SET=<문서세트>; CHK=<easyproduct-suite>/scripts/check-docs.mjs
mkdir -p "$SET/interface-requests/user/schemas"
cp <스킬>/schemas/interface-request.v1.schema.json "$SET/interface-requests/user/schemas/"
for d in $(node $CHK $SET --emit-interface-request --scope user --list-domains); do
  node $CHK $SET --emit-interface-request --scope user --domain "$d" --transport rest \
    > "$SET/interface-requests/user/interface-request-user-$d.md"
done
```

> **스키마 사본을 요청서 옆에 두는 것을 빠뜨리지 마세요.** 생성물은 자기 옆 `schemas/`를 가리킵니다.
> 없으면 점검기가 `❌ 스키마 로드 실패`를 내는데, **그 블록은 이후 검사에서 전부 빠집니다** —
> 죽은 링크도, 낡음도, 옛 배치도 침묵합니다. 점검기가 그 사실을 함께 알려 주지만, 처음 낼 때 챙기는 게 낫습니다.
>
> **재생성은 그 범위 폴더의 생성물 전체가 대상입니다.** 도메인이 사라지거나 서버 동작이 0건이 되면 파일이
> 안 나오는데, 그때 **옛 파일을 지우고 지운 목록을 보고**합니다. 안 지우면 사라진 요구가 남아 백엔드가
> 없는 화면의 인터페이스를 만듭니다. `schemas/`와 생성물이 아닌 파일은 건드리지 않습니다.

- **누가**: 프론트. 절차는 `easyproduct-screen-design` 스킬의 "인터페이스 요청서 내주기"에 있습니다
  (세트로 돌리면 suite Stage 3.8-E).
- **무엇이 담기나**: `target`이 서버인 동작만. 동작 id·화면·보냄/받음·정책·행동 규약, 그리고
  **출처 스냅샷**(그 화면 문서의 `revision`+해시). 도메인별로 갈렸으니 **출처는 하나**입니다.
- **왜 갈랐나**: ① 화면 하나를 고쳤을 때 **그 파일만 낡습니다** — 통짜면 전부가 낡음이 되어 어디가 낡았는지
  알 수 없습니다. ② user·backoffice는 **담당 개발자가 갈리는 경계**라 폴더로 나눕니다. ③ 같은 범위 안에서도
  도메인 담당자가 남의 요구까지 담긴 파일을 열 이유가 없습니다.
- **`--scope`·`--domain`은 필수**입니다. 범위를 빼면 사용자 앱과 백오피스 요구가 한 목록에 섞이고, 그러면
  아래 묶기 후보가 **권한 경계를 넘는 묶기**를 제안합니다.
- **어디에**: 기본 `interface-requests/{scope}/`. 다른 위치를 써도 되지만 **색인에 등재**해야 점검 대상이 됩니다.
- **커밋합니다** — 다른 팀·리포로 넘기는 산출물이고, 백엔드 계약의 근거이며, 신선도 판정의 기준입니다.

**`--transport`는 희망이지 확정이 아닙니다.** 그 전송이면 백엔드가 채워야 할 자리(`bindingSlots`)만
싣고 **경로·메서드 값은 지어내지 않습니다** — 그건 요구가 아니라 계약이니까요.

**손으로 고치지 않습니다.** 화면을 고치고 다시 뽑습니다. 화면이 개정되면 점검기가 알려줍니다:

```
⚠ interface-requests/user/interface-request-user-auth.md 가 낡았다
   — 출처 screens/user/screen-design-user-auth.md 가 생성 이후 바뀜
```

요청서에는 **묶을 후보**도 함께 나옵니다(아래 ③ 참고). 후보 계산은 **범위 전체**로 하고, 파일에는
**자기와 얽힌 것만** 싣습니다 — 중복은 도메인을 가로질러 생기므로 도메인 안만 보면 조용히 사라지고,
그렇다고 전부 실으면 담당자가 남의 목록을 읽게 되니까요. 상대가 다른 도메인이면 괄호로 밝힙니다:

```
- `IO.mypage.home.brief` (mypage) 는 `IO.auth.login.submit` 로 덮을 수 있음 (더 오는 값: user.id)
```

## ③ 인터페이스 계약 — 백엔드가 확정합니다

`easyproduct-backend` 스킬이 요청서를 입력으로 받아 계약을 씁니다. 요청서가 아직 없으면 화면에서 직접
추출할 수도 있지만, 그건 **프론트가 확인하지 않은 추정**이라 요청서 쪽이 우선입니다.

### 전송을 먼저 정합니다

`rest` · `grpc` · `graphql` · `ws` · `queue` 중에서 고르고 **왜 그것인지·무엇을 포기하는지**를 적습니다.
하나로 통일할 필요는 없습니다 — 조회는 REST, 서버가 밀어내는 것은 WebSocket, 정산은 큐처럼 **섞는 게 흔합니다.**

전송별 규격은 `binding`에 담습니다. **경로·메서드를 최상위에 적지 않습니다**(그건 REST 전용입니다):

| transport | binding |
|---|---|
| `rest` | `method` · `path` · `status` |
| `grpc` | `service` · `rpc` · `requestMessage` · `responseMessage` |
| `graphql` | `operationType` · `fieldName` |
| `ws` | `channel` · `event` |
| `queue` | `topic` · `key` · `deliveryGuarantee` |

### 근거(`basis`)가 필수입니다 — 출처는 여러 갈래

```json
"basis": [
  { "kind": "screen-io",  "ref": "IO.order.create.submit" },
  { "kind": "screen-io",  "ref": "IO.home.main.quickOrder" },   // 여러 화면이 같은 인터페이스를 쓴다
  { "kind": "policy",     "ref": "POL.order.serviceArea" },
  { "kind": "ops", "ref": "야간 정산 배치", "why": "세탁소에 일별 매출을 넘겨야 하는데 화면이 없다" }
]
```

- `screen-io` · `api-request`(프로젝트가 따로 가진 요청서) · `ops`(화면 없는 운영 요구) · `policy` · `legacy`.
- **개정 번호는 인터페이스마다 붙고, 스크립트가 계산합니다.** 계약 문서 하나에 인터페이스가 20개 넘게
  살면 문서 단위 개정으로는 소비자가 **"내가 맞춘 판이 아직 유효한가"**를 물을 수 없습니다.

  ```bash
  node check-docs.mjs <문서루트> --sync-revisions   # 계산해 interface-revisions.json 에 기록
  node check-docs.mjs <문서루트> --check-revisions  # 대조만 (CI용, 어긋나면 종료코드 1)
  ```

  **손으로 적지 않습니다** — 사람이 적게 하면 빕니다. 계약 문서의 `interfaces[].revision`은
  **더 올릴 때만** 씁니다: 필드는 그대로인데 **뜻이 바뀐 경우**(기계가 못 보는 변경).
  근거(`basis`)를 고쳐도 개정은 오르지 않습니다 — 계약이 바뀐 게 아닙니다.
- **필드마다 "이 값이 어디서 오나"를 셋 중 하나로 적습니다** — 저장된 값이면 `dataModel`,
  계산·가공해 만들면 `derivedFrom`(무엇으로부터 + 어떻게), 저장 안 하는 일회성이면 `transient: true`.
  **파생을 `dataModel`로 적는 것이 제일 위험합니다** — 저장 설계를 읽는 쪽이 원본을 저장한다고 오해합니다.
- **목록이면 원소 하나의 모양(`items`)까지 적습니다.** `type: "list"`에서 멈추면 받는 쪽은 원소를 모릅니다.
- **요청이 요청서 밖에서 오면 갈래를 먼저 고릅니다.** `basis`가 필수라고 아무 화면 동작 id나
  채워 넣으면 안 됩니다 — 실측에서 그렇게 붙인 4건이 **전부 진짜 결함**이었고, id가 실재하니 통과했습니다.

  | 상황 | 갈래 | 고칠 자리 |
  |---|---|---|
  | 화면에 있는데 **요청서에 없음** — `target`이 `client`/`local` | `screen-io` 유지 | **화면 설계서** |
  | 화면에 있고 `target: server`인데 요청서에 없음 | `screen-io` 유지 | **요청서 재생성** |
  | **화면 자체가 없음**(배치·웹훅·정산·이슈로 온 서버 판단) | **`ops`** + `why` | — |

  가운데 둘을 `ops`로 바꾸면 **고쳐야 할 화면 설계서가 영영 안 고쳐집니다.** 점검기가 셋을 갈라 안내합니다.
- **등기부가 없는 갈래(`ops`·`legacy`)는 `why`가 필수**입니다 — 없으면 "개발자 요구"가 아무 인터페이스나
  정당화하는 뒷문이 됩니다.
- 덕분에 **화면이 없는 API(배치·웹훅·정산)가 예외가 아니라 근거를 갖는 정식 경로**가 됩니다.

### 요구 하나에 인터페이스 하나가 아닙니다

요구 목록을 1:1로 옮기면 **같은 일을 하는 인터페이스가 화면 수만큼** 생깁니다. 계약을 짜기 전에 묶기부터 판단합니다.

| 후보 | 기본 판단 |
|---|---|
| **완전 일치**(보내고 받는 것이 같음) | 하나로 묶는다 — `basis`에 여럿 |
| **부분집합**(받는 값 5개 중 4개만 씀) | **기존 것을 그대로 쓴다** — 새로 만들지 않는다 |

기계가 후보를 짚어 줍니다(요청서 산문, `--emit-needs`의 `sameShape`·`subsetReuse`). **자동으로 묶지는 않습니다.**

**묶지 말아야 할 신호 — 하나라도 걸리면 가릅니다:**
- **권한이 다르다** — 비로그인/로그인 전용을 묶으면 넓은 쪽으로 열려 **정보가 샙니다**
  (이제 `auth`가 요구에 실리므로 **기계가 미리 갈라 냅니다** — 후보에 아예 안 올라옵니다)
- **정책이 갈린다** — 오류·차단 조건이 다릅니다
- **의미 요건이 충돌한다** — 한쪽은 멱등, 한쪽은 매번 새로
- **성격이 다르다** — 목록 대량 조회 vs 상세 1건, 캐시 가능 vs 항상 최신

부분집합으로 묶으면 **남는 값이 함께 간다**는 사실과 판단을 반드시 적습니다. 민감하거나 무거우면
가르거나 응답 축소 수단을 계약에 넣습니다 — "어차피 하나니까"로 뭉치면 **과다 전송·과다 노출**입니다.

> **이 판단은 계약을 쓰는 시점에** 합니다. 구현 단계에서 다시 하지 않습니다 — 개발자·에이전트는
> 확정된 계약을 구현하고, 새 인터페이스가 필요하면 **계약 문서로 돌아와** 근거와 함께 추가합니다.

## 점검이 양방향으로 봅니다

| 방향 | 무엇을 | 성격 |
|---|---|---|
| 요구 → 계약 | `target: server`인 동작이 어느 `basis`에도 없으면 **"덮이지 않은 요구"** | 경고 |
| 계약 → 요구 | `basis`가 빈 인터페이스 금지, 등기부 없는 갈래는 `why` 필수 | 오류 |

그 밖에: 요청서의 `ref`·데이터 변수·`policies` 죽은 링크, 저장소·`auth.mode` 실재,
**중복 동작 id**(참조가 갈림), 요청서 낡음, `target` 미분류 집계.

## 백엔드 설계 4종

| 문서 | 무엇이 사나 |
|---|---|
| 백엔드 아키텍처 | 시스템 조각·경계 · 인증 방식과 모드 등기부 · 외부 연동과 실패 처리 · 비기능 |
| 저장 설계 | 저장소 목록 · 데이터 그룹 배치 · 키 · 인덱스 · 격리 · 보존 |
| 논리 스키마 | 테이블·컬럼·논리 타입·열거값·참조와 삭제 동작 |
| 인터페이스 계약 | 위에서 설명한 것 |

**언어·프레임워크를 특정하지 않고, 저장소도 종류까지만** 정합니다(제품 선택은 구현 단계).
데이터의 뜻(데이터 모델)·제품 규칙(정책서)은 침범하지 않고, 근거가 없으면 `[확인 필요]`로 남깁니다.

## 인계

프론트와 백엔드는 인증·배포·리포지토리가 갈리는 별개 프로젝트인 경우가 많아 **spec-kit 인계장을 따로**
만듭니다(`speckit-handoff-backend.md`). **데이터 모델과 인터페이스 계약은 양쪽이 공유하는 SSOT**라
두 인계장에 모두 넣고, "이걸 바꾸면 반대쪽에 영향이 간다"를 명시합니다.

## 정직한 한계

- 요구 추출은 **`target`이 채워져 있을 때만** 됩니다. 옛 화면 설계서는 0건이 나옵니다 → [05 문서](./05-기존-세트-업그레이드.md)
- 묶기 후보는 **보내고 받는 변수만** 보고 계산합니다. 권한·성격은 그때 정해지지도 않아서 기계가 모릅니다.
- 요청서를 파일로 굳히는 이상 **낡을 수 있습니다.** 출처 스냅샷이 그걸 드러낼 뿐, 자동으로 갱신되지는 않습니다.
