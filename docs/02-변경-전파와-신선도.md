# 변경 전파와 신선도 — 결정 하나를 바꿨을 때 무엇이 따라오나

> **읽는 사람**: 이미 만든 문서 세트를 고치는 사람·에이전트. (0.7.0에서 추가)

## 무엇을 막으려는 것인가

확정된 결정 하나가 바뀔 때가 있습니다 — 예를 들어 **"개인 계정과 기관 계정은 별개"** 를
**"계정 하나 + 워크스페이스 전환"** 으로 바꾸는 것처럼요. 이때 기획서만 고치고 끝나지 않습니다.
IA·데이터 모델·정책·화면 설계·약관·시나리오가 다 따라와야 합니다.

**실제로 이렇게 샜습니다.** 에이전트가 세트 전체를 검색(grep)해 고쳤고, 기계 점검도 통과했는데
사람이 "화면 설계 진짜 끝났냐"고 되물어서야 두 건이 더 나왔습니다:

1. IA는 "N개 워크스페이스"로 고쳤는데 **화면 설계서 GNB 정의가 `(개인 ↔ 조직)` 2항 표현 그대로** — 어떤 ID도
   참조하지 않는 **산문**이라 죽은 링크가 아닙니다.
2. 화면이 "GNB에 활성 워크스페이스 항상 표시"를 요구하는데 **컴포넌트에 그 값을 받을 파라미터가 아예 없음** —
   **없는 것**은 죽은 링크가 아닙니다.

검색으로 하면 **"다 처리했다"는 완료감은 나지만 목록이 구조에서 나온 게 아니라 검색이 발견한 것**이라,
산문에만 있는 파장은 통째로 빠집니다. 그래서 세 가지를 넣었습니다.

## ① 파장 지도 — 무엇이 무엇에서 나오나

문서 **종류 사이**의 파생 관계를 스킬이 정본으로 갖고 있습니다
([propagation-map.md](../skills/easyproduct-suite/references/propagation-map.md)).

| 하류 문서 | 상류 |
|---|---|
| `ia` | 기획서·설계서 |
| `data-model` | 기획서·IA |
| `policy` | 기획서·IA·데이터 모델 |
| `terms-privacy` | 정책·기획서·데이터 모델 |
| `screen-design` | IA·디자인·데이터 모델·정책·기획서 |
| `ui-components` | 화면 설계·디자인 |
| `scenario` | IA·정책·데이터 모델·화면 설계 |
| `interface-request` | 화면 설계 |
| `backend-*` | 데이터 모델·정책·화면 설계·요청서 … |

**프로젝트가 손으로 적지 않습니다.** 이 관계는 어느 프로젝트에서나 같아서 스킬이 갖고 있고, 점검기가
당신 색인의 `docType`으로 실제 경로를 계산합니다. 표준과 다른 상류를 갖는 문서만 색인 항목에
`derivesFrom`을 적어 덮어씁니다(프로젝트 고유 문서를 파장에 편입할 때 쓰는 탈출구이기도 합니다).

## ② `revision` — 결정이 바뀌었다는 신호

각 문서 frontmatter에 **`revision`(결정 개정 번호)**가 있습니다.

- **그 문서의 결정이 바뀔 때만 +1** 합니다. 오타·문구 다듬기·서식은 올리지 않습니다.
- 올리는 주체는 **문서를 고치는 스킬**입니다. 사용자에게 묻지 않습니다.
- `version`(스키마 계약 버전)과 **다른 축**입니다. `version`은 내용이 바뀌어도 안 올라갑니다.

> **왜 해시가 아니라 번호인가**: 내용 해시만 쓰면 오타 하나에도 "상류가 바뀌었다"가 떠서, 경고가 상시로
> 뜨고 곧 무시됩니다. 그래서 개정 번호를 1차 신호로 두고, **해시는 "번호를 안 올리고 고쳤다"를 잡는 보조**로 씁니다.

## ③ 리뷰 산출물 — LLM 층에 흔적을 남긴다

점검 3층 중 소프트웨어만 산출물(리포트)이 있고 **LLM 층은 아무 흔적이 없었습니다.**
산출물이 없는 단계는 건너뛰어도 표가 나지 않고, **표가 나지 않는 단계는 건너뛰어집니다.**
성실성 문제가 아니라 설계 문제입니다.

그래서 풀 리뷰를 하면 기록을 남깁니다: `reference/reviews/review-<날짜>.md`

```json review.snapshot
{ "reviewedAt": "2026-08-10", "trigger": "계정 모델 개정", "origin": "ssot/plan.md",
  "sources": [ { "path": "ssot/ia.md", "revision": 2, "contentHash": "sha256:…" } ],
  "checked": [ { "from": "ssot/ia.md", "to": "screens/user/…", "result": "반영함", "note": "GNB N개 반영" } ],
  "outOfMap": [] }
```

`sources`의 **스냅샷이 기준선**이 됩니다. 이게 있어야 다음 점검이 "리뷰 이후 상류가 또 바뀌었는지"를 압니다.
해시는 손으로 만들지 말고 받아 쓰세요:

```bash
node <easyproduct-suite>/scripts/check-docs.mjs <문서세트> --print-snapshot
```

## 변경 전파 모드 — 검색하지 말고 이 순서로

`easyproduct-suite`의 **Step 1-B**입니다. 재진입의 세 번째 갈래예요(없으면 만든다 / 낡았으면 버전업 / **바뀐 결정을 전파한다**).

1. **진원지를 정한다** — "무엇이 바뀌었나"가 아니라 **"그 결정이 사는 문서가 어디인가"**.
   증상이 발견된 문서에서 시작하지 않습니다(증상은 대개 하류에서 보입니다).
2. **파장 지도로 하류 목록을 계산한다.** 이 목록이 작업 범위입니다.
3. **파이프라인 순서대로 내려가며 두 질문에 답한다** — 검색하지 않습니다:
   - 상류의 이 변경이 **이 문서에 무엇을 낳는가?**
   - 이 문서에 **새로 생긴 요구**가 있는가? 있다면 **다음 문서에 무엇을 낳는가?**
     *(두 번째 질문이 위 사고 2번을 잡습니다 — 화면에 생긴 요구가 컴포넌트 파라미터를 낳습니다.)*
4. 고친 문서의 **`revision`을 +1** 한다.
5. **리뷰 산출물을 남긴다.**
6. 3층 점검을 다 돌린다.

**범위 증가는 실패 신호입니다.** 2단계 목록에 없던 문서를 고치게 되면 리뷰 산출물의 `outOfMap`에 적고,
**2건을 넘으면 멈추고 지도를 다시 계산합니다.** 실제 사고에서 범위가 8→15→17→+2로 늘었는데
그 증가 자체가 신호였는데도 "꼼꼼히 챙겼다"로 읽혔습니다.

## 점검기가 알려주는 것

```
[3] 파장 · 신선도
  기준선: reference/reviews/review-2026-08-10.md (sources 24개)
  ⚠ ssot/ia.md 개정됨(r1→r2) — 하류 재검토 필요: screens/user/…, supporting/scenarios/…, …
  ⚠ ssot/plan.md 이 개정 번호 없이 수정됨(r2 그대로) — 결정이 바뀐 것이면 revision을 올리세요
  ⚠ `revision`이 없는 문서 11개 — 업그레이드 필요
  ⚠ 파장 지도에 없는 문서 종류 1종 — 파장 대상 밖 (derivesFrom으로 편입할 수 있습니다)
  ⚠ 매니페스트에 없는 문서 26건 — 점검 대상에서 빠졌다(색인 재생성 필요)
```

마지막 두 줄이 특히 중요합니다 — **조용히 빠지는 문서**를 드러냅니다. 실제 세트에서 40%가 색인에
없어 점검을 통째로 못 받고 있었는데 아무 말이 없었습니다.

## 완료 어휘 규칙

"완료 / 마무리 / 끝남"은 **기계 점검과 LLM 풀 리뷰가 모두** 통과했을 때만 씁니다.
기계 점검만 통과한 상태는 **"구조는 맞음, 의미 점검 미실행"**으로 보고합니다.

## 정직한 한계

- 파장 지도는 **문서 종류 단위**입니다. "IA의 어느 절이 어느 화면 파일에 닿는가"까지는 모릅니다 —
  볼 문서를 빠뜨리지 않게 하는 장치이지, 어디를 고칠지 짚어 주지는 않습니다.
- `revision`을 올릴지 말지는 **사람·에이전트의 판단**입니다. 산문에만 있는 결정이 바뀐 것을 기계가 알 수 없습니다.
- 리뷰 산출물은 **형식만 채워도 통과**합니다. 그 대신 그 사실이 기록으로 남습니다.
