# 문서 세트 훑어보기 — 무엇이 있고 어떻게 이어지나

> **읽는 사람**: 이 스킬들로 문서를 만드는 사람(기획자·1인 개발자·에이전트).
> 개별 스킬 사용법이 아니라 **세트 전체의 지도**입니다. 각 스킬의 자세한 절차는 그 스킬 `SKILL.md`에 있습니다.

## 한 장으로 보는 흐름

```
아이디어
  └─ 기획서 · 설계서 ─────────────── 무엇을·왜 만드나
       └─ 화면·기능 구조(IA) ──────── 어떤 화면·기능으로
            ├─ 데이터 모델 ────────── 어떤 정보를 다루나  ← 데이터의 뜻은 여기가 원본
            ├─ 디자인 컨셉 ────────── 어떤 색·글꼴·느낌으로
            └─ 정책서 · 약관 ───────── 어떤 규칙·약속으로
                 └─ (옵트인) 화면 설계서 ── 각 화면에 뭐가 보이고 뭘 누르면 어떻게 되나
                      ├─ UI 컴포넌트 인벤토리
                      ├─ (옵트인) 시나리오 ── 여러 화면을 꿰는 사용자 여정
                      ├─ 인터페이스 요청서 ── 서버에 필요한 것(기계 생성) → 03 문서
                      └─ (옵트인) 백엔드 설계 4종 ─────────────────→ 03 문서
                           └─ spec-kit 인계 안내문 → 개발 착수 ────→ 04 문서
```

한 번에 다 만들려면 **`easyproduct-suite`** 하나만 부르면 됩니다. 순서·질문·이어붙이기를 그 스킬이 관리합니다.
하나만 필요하면 해당 스킬을 직접 부르세요 — **각 스킬은 독립 동작**합니다.

## 문서마다 "결정이 사는 곳"이 다릅니다 (SSOT)

문서가 겹치는 말을 할 때 **어느 쪽이 진실인지**가 정해져 있습니다. 이걸 알면 고칠 곳을 헷갈리지 않습니다.

| 무엇을 정하나 | 그 결정이 사는 문서 |
|---|---|
| 제품이 무엇이고 왜 만드나 | 기획서 `ssot/plan.md` |
| 어떤 화면·기능이 있나 | 화면·기능 구조 `ssot/ia.md` |
| 데이터의 **뜻과 필드 구성** | 데이터 모델 `ssot/data-model.md` ← 기획서보다 우선 |
| 색·글꼴·여백 값 | 디자인 컨셉 `ssot/design-concept.md` |
| 제품 규칙(권한·환불·보존) | 정책서 `ssot/policy.md` |
| 화면 하나하나의 상세 | 화면 설계서 `screens/…` ← 화면 상세는 IA보다 우선(범위는 IA 안) |
| 데이터가 **어디에 어떤 모양으로 놓이나** | 백엔드 저장 설계·논리 스키마 |
| **어떤 전송으로 어떻게 주고받나** | 백엔드 인터페이스 계약 |

**파생물은 SSOT가 아닙니다** — 시나리오·기능 관계도·색인·인터페이스 요청서는 원본에서 뽑아낸 것이라,
원본과 어긋나면 **원본이 이깁니다.** 손으로 고치지 말고 다시 뽑으세요.

## 폴더 구조

```
ssot/                기획서·설계서·IA·데이터 모델·디자인·정책·약관·UI 인벤토리
  └─ backend/        (옵트인) 백엔드 아키텍처·저장 설계·논리 스키마·인터페이스 계약
screens/             화면 설계서 — user/ · backoffice/ 로 갈림
supporting/          유저 스토리·유스케이스·시나리오 (보강자료)
reference/           디자인 3안 미리보기, 기능 관계도, 풀 리뷰 기록 (참고물)
interface-requests/  백엔드에 넘길 인터페이스 요청서 (기계 생성 인계물)
schemas/             각 문서의 검증 계약(JSON Schema) 사본
temp/                목업 등 재생성 가능한 참고물 (git 추적 제외)
00-index.md          그 시점의 문서 목록 스냅샷 (git 추적 제외)
```

## 문서 하나의 생김새 — 사람 층 + 기계 층

각 문서는 **사람이 읽는 본문**과 **소프트웨어가 읽는 블록**을 함께 담습니다.

```markdown
---
doc_type: ia          ← 무슨 문서인지
version: 1            ← 검증 계약(스키마)의 버전
revision: 2           ← 이 문서의 결정이 몇 번째 세대인지  → 02 문서
ssot: prose           ← 산문이 원본인지, 표가 원본인지
machine:
  tag: ia.features    ← 아래 json 블록을 찾는 이름
  schema: ../schemas/ia.v1.schema.json
---

## FEAT.auth.login — 로그인          ← 사람이 읽는 정의
이메일로 로그인한다.

```json ia.features                  ← 같은 내용의 기계 미러
{ "features": [ { "id": "FEAT.auth.login", … } ] }
```
```

- **산문이 원본이고 블록은 미러입니다**(데이터 모델만 표가 원본). 산문을 고치면 블록을 다시 만듭니다.
- 블록 덕분에 **소프트웨어가 문서끼리 어긋난 곳을 찾아냅니다** — 화면이 없는 기능을 가리키거나,
  데이터 모델에 없는 변수를 쓰거나 하는 것을요.
- 필드의 정확한 뜻과 점검 규칙은 **[checker-guide](../skills/easyproduct-suite/references/checker-guide.md)**에 있습니다(점검기를 만드는 사람용 계약서).

## ID로 서로를 가리킵니다

문서들은 서로를 **ID**로 참조합니다. 앞글자가 곧 "어느 문서에서 찾을지"입니다.

| ID | 무엇 | 어디에 정의 |
|---|---|---|
| `FEAT.주문.예약` | 기능·화면 | IA / 화면 설계서 |
| `IO.주문.예약.제출` | 화면의 **동작** | 화면 설계서 |
| `user.email` | 데이터 항목 | 데이터 모델 |
| `POL.주문.취소` | 제품 규칙 | 정책서 |
| `UI.button.primary` | 공통 컴포넌트 | UI 인벤토리 |
| `SCN.가입.온보딩` | 시나리오 | 시나리오 |
| `BEITF.user.주문.생성` | 백엔드 인터페이스 | 인터페이스 계약 |

가리킨 ID가 실제로 없으면 **죽은 링크**로 잡힙니다. 이게 "문서끼리 안 맞는 것 같다"를 기계가 대신 봐 주는 방식입니다.

## 점검은 세 층입니다

| 층 | 누가 | 무엇을 | 언제 |
|---|---|---|---|
| **소프트웨어** | `check-docs.mjs` | ID 형식 · 죽은 링크 · 스키마 위반 · 파장·신선도 | 아무때나, 항상 세트 전체 |
| **LLM** | 에이전트 | 산문이 뜻을 제대로 담았나 · 미러가 산문과 맞나 | 풀 리뷰 때만 |
| **사람** | 당신 | 이게 정말 원하는 제품인가 | 게이트에서 |

**기계 점검 통과 = "구조는 맞음"이지 "검증 완료"가 아닙니다.** 그래서 풀 리뷰를 하면 그 흔적을
`reference/reviews/`에 남깁니다 → [02 문서](./02-변경-전파와-신선도.md)
