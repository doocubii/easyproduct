# SDD 하네스 연동 — 문서가 개발에서 실제로 지켜지게 하기

> **읽는 사람**: spec-kit(SDD)으로 개발하는 개발자·코딩 에이전트. (0.6.0에서 추가)
> 문서를 만드는 흐름과는 **별개 층**입니다 — 비전문가는 이 문서를 안 읽어도 됩니다.

## 무엇이 문제인가

spec-kit 프로젝트에서 SDD("소스부터 고치지 않는다 · spec→plan→tasks→implement")는
**헌법·CLAUDE.md에 적힌 규범일 뿐 실행 게이트가 아닙니다.** 실제로 강제되는 층(린트·타입·테스트·CI)은
**코드 품질**만 보고, **"이 코드가 승인된 spec에서 나왔는가"는 아무도 검사하지 않습니다.**

그래서 규범이 속도·자율 지시와 경쟁하면 집니다. 실전에서 세 가지로 샙니다:

| | 실패 | 왜 안 잡히나 |
|---|---|---|
| **C1** | 수정 요청에 **소스부터 고침** | `verify`는 spec-first든 code-first든 똑같이 통과 |
| **C2** | **상위 문서(기획서·SSOT·헌법)가 바뀌었는데 spec-kit 흐름을 안 탐** | 아무도 상위 문서를 안 봄 |
| **C3** | **상위와 충돌하는 spec 수정** | spec 내용을 보는 검사가 없음 |

`easyproduct-sdd-harness`가 그 규범을 **실행 게이트로 승격**합니다. 규범을 만들지는 않습니다 —
헌법·CLAUDE.md에 적힌 것을 기계가 지키게 할 뿐이고, 규범이 없으면 "보강 권고"를 리포트에 남깁니다.

## 7규칙 3축

| 축 | 규칙 |
|---|---|
| **코드 층**(C1) | **① 출처** 관장 파일마다 `@sdd <slug>` 태그 · **② 완결** 슬라이스에 spec/plan/tasks + 핀 파일 · **③ 결합** 코드가 바뀌면 그 슬라이스도 바뀌어야 |
| **전파 층**(C2) | **⑥ 역결합** 상위 문서만 바뀌고 슬라이스가 안 바뀌면 위반 · **④ 신선도** 슬라이스가 핀한 상위의 **개정 축**(easyproduct=`revision`)+`contentHash`가 현재와 일치해야 |
| **내용 층**(C3) | **⑤ 근거** spec/plan이 참조한 앵커가 상위 등기부에 실재 + 근거 0인 요구 금지 · **⑦ 리뷰 기록** spec/plan을 고쳤으면 상위 대조 기록을 남겨야 |

**C2 축이 이 하네스의 핵심 가치**입니다 — spec-kit 본체도, 커뮤니티 확장(CI Guard·Gates·Blueprint)도
이걸 보지 않습니다. spec-kit은 **"spec이 세계의 시작"**이라 가정해서 **spec 위층이 존재한다는 모델이 없기** 때문입니다.
기획서를 먼저 만드는 팀에서만 생기는 실패라 생태계가 아직 안 봅니다.

## easyproduct 문서가 있으면 정밀해집니다 (없어도 동작합니다)

하네스는 **easyproduct 문서를 전제하지 않습니다.** 순수 spec-kit 프로젝트에서도 완결 동작합니다.
다만 우리 문서가 있으면 **문서 어댑터**가 켜집니다:

| | easyproduct 문서 있음 | 없음(generic) |
|---|---|---|
| ⑤ 근거의 등기부 | 기계 블록에서 `FEAT`·`DATA`·`POL`… ID 수집 → **정확한 대조** | 헤딩·`REQ-*` 규칙, 없으면 ⑤ off |
| ④⑥ 영향 범위 | **앵커 단위**로 좁힘 | 파일 단위 |
| **개정 축** | frontmatter **`revision`**(결정 개정 번호) | semver 라인(`**Version**: 1.0.0`) |

즉 **[02 변경 전파](./02-변경-전파와-신선도.md)가 문서 세트 안에서 하는 일을, 하네스는 문서→spec→코드 축에서** 합니다.

## 두 점검기는 별개입니다

```
check-docs.mjs      문서 세트 내부      기획서 ↔ IA ↔ 화면 ↔ 데이터 ↔ 정책
sdd-check.mjs       문서 → spec → 코드   상위 문서 ↔ specs/<slug>/ ↔ 소스 파일
```

서로 import하지 않고 전제하지도 않습니다. 실무에서는 **둘 다 CI에 나란히** 겁니다.
순서는 **문서 세트를 먼저 정합시키고 → 그다음 spec 전파**입니다(반대로 하면 아직 흔들리는 상위를 spec에 핀하게 됩니다).

| 사건 | 누가 잡나 |
|---|---|
| `ia.md`가 바뀌었다 → **spec 슬라이스**가 재검토돼야 | sdd-harness ④ |
| `ia.md`가 바뀌었다 → **화면 설계서·요청서**가 따라가야 | check-docs 파장 |
| spec을 고쳤다 → 상위 대조 기록 필요 | sdd-harness ⑦ |
| 문서 세트를 고쳤다 → 풀 리뷰 기록 필요 | check-docs |

> **둘 중 하나만 걸면 사각이 생깁니다.** 실제로 한 프로젝트가 `check-docs`를 CI에 안 물려 두어,
> 새로 생긴 채널(요청서 96건)이 **어느 쪽에서도 검증되지 않았습니다.** 하네스 설치 조사(Step 0-6-1)가
> 세트 문서를 발견하면 이걸 확인하고 함께 걸자고 제안합니다.

## 개정 축은 문서 계열마다 다릅니다

④ 신선도는 **"핀한 뒤 상위가 바뀌었나"**를 봅니다. 그 "바뀌었나"를 재는 축이 계열마다 다릅니다.

| 어댑터 | 축 | 왜 |
|---|---|---|
| `easyproduct` | **`revision`** | frontmatter `version`은 **payload 계약(스키마) 버전**이라 내용이 바뀌어도 안 올라갑니다 |
| `generic` | `version`(semver 라인 등) | 그 문서가 가진 유일한 버전 표식입니다 |

**0.10.5 전에는 둘 다 `version`을 축으로 삼았습니다.** easyproduct 문서에서 그 값은 사실상 안 변하므로
④가 **항상 해시 갈래로 떨어졌고**, "결정 개정"과 "문구 손질"이 한 덩어리가 됐습니다. 게다가 FIX 문구가
**"상위 문서의 `version`을 먼저 올려라"**여서, 시키는 대로 하면 **스키마 계약 버전이 오염**됐습니다.

> 실측: 한 프로젝트에서 v1 스키마 문서에 `version: 13`이 박혔고, 반대로 계약대로 `revision`만 올린
> 변경은 하네스가 계속 위반으로 보고해 **"레포 전역 규약 위반"이라는 오진**까지 나왔습니다.
> 경고 60건 중 실제 요구 변화는 **0건**이었습니다.

이제 이렇게 갈립니다.

```
④ 신선도
  ✗ app_docs/ssot/ia.md 개정됨(revision 1→2)          ← 진짜 할 일. 재검토가 필요합니다
  ⚠ app_docs/ssot/ia.md가 핀 이후 수정됨(revision 1 그대로 · 내용 해시 불일치)
      → 내용을 확인하고 핀을 갱신하세요. 결정이 바뀐 것이면 상위 문서의 revision을 올립니다 —
        version은 payload 계약(스키마) 버전이라 올리지 않습니다.
```

핀 파일도 축을 그대로 적습니다.

```jsonc
{ "path": "app_docs/ssot/data-model.md", "revision": "2", "contentHash": "sha256:…" },
{ "path": ".specify/memory/constitution.md", "version": "2.2.0", "contentHash": "sha256:…" }
```

**옛 핀(`version`만 있는 것)도 그대로 읽습니다** — 축이 `revision`일 때 `revision`이 없으면 `version` 값을
씁니다. 다만 그 값은 스키마 계약 버전이라 안 변하므로, **핀을 한 번 재생성해 축을 옮기는 편이 낫습니다.**

### 이미 `version`이 오염됐다면 — 순서가 중요합니다

`check-docs`가 **"`version`이 스키마 계약과 다른 문서 n개 — 이행 필요"**로 집계합니다.
그냥 `1`로 되돌리면 **슬라이스 핀이 한꺼번에 깨집니다.** 이 순서로 하세요.

1. **핀을 먼저 재생성**합니다(그 시점 값 그대로 — 해시 기준이라 정상입니다).
2. 그다음 `version`을 계약 값(`1`)으로 되돌리고 **핀을 다시 갱신**합니다.
3. 2·3에서 ④가 한 번씩 뜨는데, 실제로 내용이 안 바뀐 것이니 확인 후 넘기면 됩니다.

## 세트가 자라면 정책이 뒤처집니다 — 그걸 보고합니다

`sdd-policy.json`의 `idPrefixes`·`globs`는 **프로젝트가 손으로 유지**합니다. 그래서 문서 세트가 새
네임스페이스나 새 폴더를 얻으면 정책이 못 따라가고, **검사받던 참조가 검사 안 받는 참조로 조용히 바뀝니다.**

실제로 그랬습니다 — 0.8.0이 `IO.*`를 1급 앵커로 만들었는데 어느 프로젝트의 `idPrefixes`에는 `IO`가 없었고,
`APIREQ.*` 참조를 `IO.*`로 옮기자 그 96건이 **죽은 링크로도 안 잡히고 근거로도 안 세어지는** 상태가 됐습니다.
하네스는 통과했지만 **통과한 게 아니라 안 보인 것**이었습니다.

그래서 두 가지를 보고합니다(위반이 아니라 **note** — 오탐 여지가 있고 판단은 사람 몫입니다):

```
note: ⑤ 등기부에 없는 접두사 참조: IO(96건) · BEITF(12건)
       → upstreamDocs.anchorRegistry.idPrefixes 에 넣으면 검사받는다.
       → 지금은 이 참조들이 죽은 링크로도 안 잡히고 근거로도 안 세어진다(검사 밖).
note: ④⑥ 매니페스트에 있는데 upstreamDocs.globs가 안 덮는 상위 문서 96건 (interface-request 96)
       → 그 문서들은 상위 변경 감지(⑥)·신선도(④) 밖이다.
```

앞의 것은 어댑터와 무관하게 돌고(순수 spec-kit에서도), 뒤의 것은 `docsAdapter: "easyproduct"`일 때
세트 색인(`00-index.md`)의 매니페스트와 대조합니다.

> **정책을 매니페스트로 대체하지는 않습니다.** 정책은 "무엇을 감시하는지"를 사람이 읽을 수 있어야 하고,
> 런타임에 남의 색인에서 끌어오면 그 성질이 사라집니다. **채우는 것은 설치·갱신 때, 어긋남은 매번 보고**입니다.

## 설치 — 조사부터, 그리고 기존 게이트 위에 얹기

스킬을 부르면 **9항목을 조사**해 리포트를 내고 확정을 받은 뒤 설치합니다: spec-kit 유무 · 스택 ·
상위 문서 형식(어댑터 결정) · SDD 규범이 실제로 적혀 있나 · 기존 게이트 위치 · **이미 깔린 spec-kit 확장** ·
관장 사각 · 하네스 설치 상태 · **모노레포 여부**.

배선은 **새 파이프라인을 만들지 않고 기존 것에 얹습니다**:

| 층 | 무엇 | 성격 |
|---|---|---|
| ⓪ 규범 상주 | `SessionStart` 훅 — "이 프로젝트엔 SDD 게이트가 있다 + 열린 슬라이스" 주입 | 예방 |
| ① 빠른 피드백 | `PostToolUse` 훅에 `--changed`(위반 시 `exit 2`로 에이전트에 주입) | 로컬 |
| ② 완료 게이트 | `verify`에 `--full` | 로컬 |
| ③ **실제 강제** | **CI 잡에 `--full`** — 실패 = 머지 차단 | **차단** |

- **모노레포면 `specsDir`가 두 마디 이상입니다**(`frontend-user/specs`). 0.10.0 전에는 검사기가 슬러그를
  `split('/')[1]`로 뽑아 **③ 결합이 항상 발화**했습니다 — `warn`에선 소음이지만 `block`으로 졸업하는
  순간 관장 파일을 건드리는 모든 커밋이 막힙니다. 0.10.0에서 고쳤으니 **검사기 사본을 갱신**하세요.
- **CI는 전체 히스토리가 필요합니다**(③⑥이 merge-base를 씀) — GitLab `GIT_DEPTH: 0`, GH Actions `fetch-depth: 0`.
- **`mode: "warn"`은 verify·CI 층에만 적용됩니다** — 훅은 도입 기간에도 살아 있습니다.
- 이미 **Gates**가 깔렸으면 그 3경계에 검사기를 등록하고, **CI Guard**가 있으면 겹치는 ②를 끄고 위임합니다.

## 브라운필드 도입 — 핀 먼저, 태그 나중

무태그 코드가 많으면 켜는 순간 전부 위반이라 **`mode: "warn"`으로 시작**합니다. 순서가 중요합니다:

1. **슬라이스마다 `sources.json` 핀을 채운다** — 핀이 없으면 ④가 침묵해서 **핵심 가치인 C2가 계속 0**입니다.
   비용은 슬라이스당 파일 하나인데 가장 크게 새는 구멍을 바로 막습니다.
2. **관장 파일에 `@sdd` 태그를 백필**한다(①③ 가동).
3. ⑤⑦을 튜닝 후 `block`으로 승격.

> 팀은 기계적으로 쉬운 **태그부터** 손대기 마련이라, 몇 주 동안 ④가 침묵한 채 상위 변경이 샙니다.
> 실제 프로젝트 실측: **상위 문서 변경 커밋의 75%가 슬라이스 무동반**이었습니다.

## 슬라이스가 계속 늘어나는데 정상인가요?

**정상이 아닙니다. 접으셔도 됩니다.**

규칙 일곱이 전부 **변화**에 반응합니다 — 코드가 바뀌면, 상위 문서가 바뀌면, spec이 바뀌면 웁니다.
그런데 **"이건 끝났다"를 말하는 자리가 없었습니다.** 그래서 고칠 때마다 새로 열게 되고,
슬라이스는 가만두면 **단조증가**합니다.

실사용 제보(다섯 달, 파이썬 백엔드 한 트랙):

```
슬라이스 78개   →   정리 후 23개
  제품 기능 21 · 버그 고침 22 · 계약 문서 정합 19 · 하네스 작업 7 · 기반 6 · 정리 3
  18개는 관장 소스를 한 줄도 안 고쳤다

시험 파일 58 → 36   (시험 수는 그대로)
게이트 100초 → 38.6초
```

### 왜 늘어났나 — 문구 하나가 컸습니다

③ 결합이 울 때 주던 두 갈래가 이렇게 읽혔습니다:

| 문구 | 읽히는 뜻 |
|---|---|
| "spec/plan/tasks를 **먼저 갱신**하거나" | 이미 닫힌 슬라이스를 **다시 여는 것** |
| "**면제** 트레일러" | 규칙을 **피하는 것** |

그래서 **문구에 없는 셋째 길 — 새 슬라이스를 만들고 태그를 옮기는 것 — 이 제일 떳떳해 보였습니다.**
그것만 19개가 됐습니다.

**지금은 「흡수」라고 말합니다:**

```
이 변경을 흡수할 슬라이스의 spec/plan/tasks를 갱신하라 — 기존 슬라이스여도 된다
(새로 만들 필요 없다). 무관한 변경이면 커밋 트레일러 `SDD-Exempt: …`로 면제.
```

**검사는 하나도 안 약해졌습니다** — 막는 것은 그대로이고 사람에게 하는 말만 바뀌었습니다.

### 접는 기준 — 「그것이 지금 **어디에 사나**」

「코드가 있나」가 아닙니다. **태그가 잇는 것만** 슬라이스가 필요합니다.

| 지금 어디에 사나 | 슬라이스는 |
|---|---|
| **코드에 산다** — `@sdd` 태그가 잇는다 | **남습니다.** 일이 끝났어도 **결속 기록**입니다 — 껍데기가 아닙니다 |
| **문서에 산다** — 규격 문서·계약이 정본 | 접습니다. 슬라이스는 **운반 수단**이었습니다 |
| **슬라이스에만 산다** | 먼저 옮기고 → 접습니다 |

코드 0줄이어도 접을 수 있고, 코드를 고친 슬라이스도 접을 수 있습니다.

> **코드가 규격 문서를 바로 가리키게 하지 마세요.** 규격 문서는 **아직 구현될 준비가 안 된 문서**이고,
> 그것을 구현으로 옮기는 일이 슬라이스입니다. 코드가 문서로 직행하면 **SDD 절차를 거친 코드와
> 건너뛴 코드가 구분되지 않습니다.** 슬라이스를 없애고 싶으면 답은 **흡수**입니다 —
> 비슷한 기능을 정의한 슬라이스가 그 태그와 산출물을 받습니다.

### 접는 순서

1. **구속력 있는 태그만 세세요.** `allowlist` 안의 태그는 **검사기가 안 봅니다**(장식입니다).
   제보자는 이걸 몰라 시험·하네스의 태그까지 세는 바람에 **처음에 일곱 개밖에 못 줄였습니다.**
2. **그 슬라이스만 핀한 상위 문서가 있는지** 보세요. 있으면 그냥 접었을 때 그 문서가 바뀌어도
   **④가 아무 데서도 안 웁니다.** 핀을 먼저 옮기세요.
3. **다른 문서가 그 슬라이스를 이름으로 참조하는지** 보세요.
4. **접고 게이트를 돌리세요.** ②가 남은 참조를 잡아 줍니다 — 빈 폴더도 남기지 마세요.

### 검사기가 후보를 세어 줍니다

`--full`을 돌리면 **정보 등급**으로 나옵니다. **위반이 아니라 종료코드도 안 바뀝니다:**

```
note: 구속력 있는 태그가 없는 슬라이스 19개 — 접을 수 있는지 보세요: 012-harness-apply, …
       (allowlist 안 태그는 안 셉니다 — ③이 그걸 안 보기 때문입니다)
       → 접는 순서: SKILL.md 「슬라이스를 언제 열고 언제 접나」
note: 이 슬라이스만 핀한 상위 문서 4건 — 그냥 접으면 ④가 아무 데서도 안 웁니다
       012-harness-apply → harness/APPLIED.md
       → 접기 전에 핀을 옮기세요(접는 순서 2번)
```

> ⚠ **아직 코드를 안 쓴 진행 중 슬라이스도 걸립니다.** 판단은 사람이 합니다.

## 정직한 한계

7규칙은 **의례·공존을 강제**할 뿐 **인과적 파생·의미 정합을 검증하지 않습니다.**
태그만 붙이기 · 슬라이스 no-op 편집 · 핀 숫자만 갱신 · 리뷰 기록 형식만 채우기로 우회할 수 있고,
⑤는 앵커가 **실재**하는지만 보지 **옳게 해석했는지**는 못 봅니다.

**기계 통과 ≠ 검증 완료.** 이 하네스의 효용은 프로세스 생략을 **가시화·유료화**하는 것이고,
우회하면 그 흔적이 **커밋 히스토리와 리뷰에 남는다**는 데 있습니다.
그리고 에이전트가 로컬 훅 배선 자체를 고칠 수 있으므로 **CI가 최종 backstop**입니다.
