# 기존 세트 업그레이드 — 예전에 만든 문서를 최신 계약으로

## 어떻게 시작하나 — 그냥 말하면 됩니다

```
"우리 문서 세트 현행화해줘"
"낡은 형식 고쳐줘"
"점검기가 경고를 내는데 고쳐줘"
```

오케스트레이터(`easyproduct-suite`)가 발동해 **Step 1 재진입**으로 갑니다. 거기서 낡은 구조를
갈래별로 감지해 **각 스킬의 버전업(gap-fill) 절차**로 보냅니다 — 처음부터 다시 만들지 않고
**빠진 것만** 채웁니다.

문서 한 종류만 올리고 싶으면 그 스킬을 직접 부르셔도 됩니다("계약 현행화해줘", "IA 현행화해줘").

### 점검기를 복사해 쓰기 (CI·다른 개발자 기계용)

점검기는 **스킬 안에** 있습니다. 그래서 스킬이 깔린 컴퓨터에서만 돕니다 — **CI 서버나 동료의 기계에는
스킬이 없습니다.** 그럴 때는 점검기를 프로젝트 안에 **복사해 두고 쓰시면 됩니다.** 무의존 단일 파일이라
그것만으로 돕니다.

복사할 것은 셋입니다(스킬 폴더 → 프로젝트, 예: `harness/vendor/`):

```
easyproduct-suite/scripts/check-docs.mjs              점검기 본체
easyproduct-suite/assets/propagation-map.json         파장 지도    ┐ 점검기가
easyproduct-suite/assets/anchor-prefixes.json         앵커 등기부  ┘ 실행 중 읽습니다
easyproduct-suite/references/checker-guide.md         계약 정본(사람이 읽는 문서)
```

**폴더 구조를 그대로 두세요.** 점검기가 자기 위치 기준(`../..`)으로 자산을 찾습니다 — 평평하게 두면
파장 지도 조회가 **경고 없이 생략**됩니다.

**스키마는 복사하지 않습니다.** 문서 세트에 이미 함께 나갑니다(각 문서 옆 `schemas/`).
그래서 복사본으로 돌리면 "스키마 사본 일치 **확인 못함**"이 뜨는데, **그건 정상입니다** —
점검기가 무엇을 못 봤는지 밝히는 것뿐입니다.

### ⚠ 스킬이 올라가면 점검기도 올라갑니다 — 복사본은 그때의 사본입니다

**점검기는 스킬과 함께 자랍니다.** 새 버전이 나오면 검사가 붙는데, **옛 복사본에는 그 검사가 아예
없습니다.** 그러니 **스킬을 업그레이드하셨으면 복사본도 다시 복사하세요.**

**안 하면 조용히 뒤처집니다.** 옛 복사본은 새 검사를 모르니 **아무 말 없이 통과**시킵니다 —
고칠 것이 있는 줄도 모른 채 초록불을 받습니다.

> 실측: 복사본이 세 판 뒤처져 있어 **새 검사 여섯이 한 건도 안 돌았고**, 그 사이 계약 문서의
> **실제 위반이 가려져** 있었습니다.

**복사본 폴더에 `VERSION` 파일을 두고 그때의 세트 버전을 적어 두세요.** 나중에 "언제 것인지"를 아는
유일한 단서입니다.

> ⚠ **사본 신선도를 검사하신다면, 기준 자리 자체가 낡을 수 있습니다.** 저장소에 담아 둔 스킬 사본을
> 기준으로 삼으면(스킬이 안 깔린 기계·CI에서도 돌아야 하니 흔한 선택입니다), **그 기준이 뒤처졌을 때
> 검사가 조용히 통과합니다.** 실사용 제보: 기준 사본 `0.12.9` · 설치본 `0.12.10` · 벤더 `0.12.9` →
> 기준과 같으니 **통과**. 경로만 비교하지 말고 **`VERSION` 값도 함께** 보세요.

### 벤더 사본을 쓰신다면 — 갱신할 것이 셋입니다

점검기를 저장소에 복사해 CI에 물려 쓰신다면, 새 버전이 나올 때 **셋을 함께** 갱신하세요.
하나라도 빠지면 조용히 어긋납니다:

| 무엇 | 어디 | 안 하면 |
|---|---|---|
| **점검기** | `vendor/easyproduct-suite/scripts/check-docs.mjs` | 새 검사가 아예 안 돕니다 |
| **자산** | `vendor/easyproduct-suite/assets/*.json` (파장 지도·앵커 등기부) | 파장·참조 판정이 옛 기준입니다 |
| **스키마** | 문서 옆 `schemas/*.json` **+ 벤더가 품은 사본** | 새 칸이 "스키마에 없는 키"로 걸리고, **기존 위반이 가려집니다** |

**세 번째가 제일 조용합니다.** 실측에서 벤더가 `0.11.0`에 멈춰 있어 새 검사 여섯이 한 건도 안 돌았고,
사본이 옛것이라 **계약 문서의 실제 스키마 위반 3건까지 가려져** 있었습니다.

벤더 폴더에 `VERSION` 파일을 두고 세트 버전을 적어 두면 "언제 것인지"가 한눈에 보입니다.

> **점검기와 스키마 사본을 먼저 갱신하세요.** 벤더 사본을 쓰신다면, 옛 사본으로는 **새 경고 자체가
> 안 뜹니다.** `check-docs.mjs`와 문서 옆 `schemas/*.json`을 최신 스킬 자산으로 맞춘 뒤 시작하세요.

> **gap-fill은 "구조만 맞춘 것"이지 "검증 완료"가 아닙니다.** 채운 뒤 반드시 풀 리뷰를 이어붙이세요.


> **읽는 사람**: 이미 문서 세트를 가진 사람·에이전트.
> **원칙**: 스킬이 계약을 바꾸면 **기존 문서를 올려 주는 경로도 함께** 냅니다. 새 기능을 신규 사용자만
> 얻고 문서를 이미 가진 사람이 못 얻으면 반쪽 릴리즈입니다(`CLAUDE.md`의 명문 원칙).

## 먼저 점검기를 돌리세요 — 무엇을 해야 하는지 알려 줍니다

```bash
node <easyproduct-suite>/scripts/check-docs.mjs <문서세트>
```

무엇이 낡았는지 **집계해서** 말해 줍니다. 아래는 실제 세트(문서 65개)에서 나온 출력입니다:

```
⚠ 매니페스트에 없는 문서 26건 — 점검 대상에서 빠졌다(색인 재생성 필요)
⚠ `revision`(결정 개정 번호)이 없는 문서 11개 — 업그레이드 필요
⚠ `target` 미분류 동작 70건 — 업그레이드 필요(server/local/client 판정)
⚠ 폐기된 `data.io[].op` 2건 — 이관 필요
⚠ 파장 지도에 없는 문서 종류 1종 — 파장 대상 밖
⚠ 스키마 사본이 스킬 자산과 다름 — 어느 쪽이 최신인지 확인 필요
```

이 목록이 곧 할 일입니다. 하나씩 봅니다.

## ① 매니페스트에 없는 문서 — 색인 재생성

**가장 먼저 하세요.** 색인(`00-index.md`)에 없는 문서는 스키마 검증·죽은 링크·파장에서 **통째로 빠지는데
아무 표가 안 납니다.** 실제 세트에서 40%가 그 상태였습니다.

- `easyproduct-suite`에 "색인 다시 만들어줘"라고 하면 Stage 4-2가 현재 폴더를 훑어 새로 씁니다.
- 프로젝트 고유 문서(세트 표준 밖)도 등재하세요. 등재하면 점검 대상이 됩니다.

## ② `revision`이 없는 문서 — 개정 번호 채우기

**무엇**: 각 문서 frontmatter에 `revision`(결정 개정 번호)이 없습니다 → 파장·신선도의 1차 신호가 빕니다.

**어떻게**: 그 문서의 스킬을 **버전업(gap-fill)** 으로 부릅니다. 내용은 손대지 않고 **`revision: 1`만** 채웁니다.
과거에 몇 번 고쳐졌든 **지금을 1세대로 봅니다** — 이력을 지어내지 않습니다.

## ③ `target` 미분류 동작 — 화면 설계서 gap-fill

**무엇**: 화면 설계서의 `data.io[]`에 `target`(server/local/client)이 없습니다.

**왜 중요한가**: 없으면 백엔드 설계가 **로컬 저장·화면 이동에까지 서버 인터페이스를 지어냅니다.**
그리고 인터페이스 요청서 추출이 **0건**이 됩니다(→ [03 문서](./03-프론트엔드-백엔드-연동.md)).

**어떻게**: `easyproduct-screen-design`의 "버전업(gap-fill)" 절차대로 셋을 함께 채웁니다.

1. **`target` 부여** — 각 동작이 누구와 주고받는지 **산문을 읽고** 판정합니다("서버에 저장" / "기기에 임시저장" /
   "목록만 다시 정렬"). **애매하면 지어내지 말고** `[확인 필요: target]`을 산문에 남기고 비워 둡니다.
2. **`id` 부여** — `IO.<도메인>.<화면>.<동작>` 꼴. 동작 이름을 영문으로 옮겨 짓되 **중복되지 않게** 합니다
   (중복이면 점검기가 오류로 잡습니다 — 참조가 갈리기 때문).
3. **`op` 이관** — 폐기된 필드입니다. 값이 있으면 백엔드 인터페이스 계약의 `basis`로 옮기고 비웁니다.
   백엔드 문서가 아직 없으면 그대로 두고 백엔드 설계 때 이관합니다.

**함께 권합니다**: 산문에 있는 규칙·행동 규약을 `policies`(`POL.*`)·`semantics`에 담으세요.
안 담으면 백엔드가 오류 근거·멱등·정렬을 정할 재료가 없습니다. 점검기가 비어 있는 동작 수를 알려 줍니다.

## ③-0 인증 요건(`auth`)이 없음 — 누가 쓸 수 있는지 채우기

```
❌ 인증 요건(`auth`)이 없는 서버 동작 135건 — 누가 쓸 수 있는지가 요청서에서 빠진다
     · IO.admin.billing.list.load (FEAT.admin.billing.list)
```

**오류입니다**(경고가 아닙니다). 옛 문서에는 이 필드가 없어서, 요청서에 **누가 쓸 수 있는지가 통째로
빠진 채** 백엔드로 나갔습니다. 실측 세트에서 서버 동작 135건 중 82건이 권한 정보 없이 나갔고
**그중 27건이 운영자 전용**이었습니다 — 청구 목록·상품 노출 토글 같은 것들입니다.

**하나씩 타이핑하지 않습니다.** 아래 규칙으로 초안을 만들고 확정만 하세요(실측 세트에서 **약 67%**를 덮습니다).

| 신호 | 초안 |
|---|---|
| `FEAT.admin.*` 이거나 백오피스 범위 | `{ "required": true, "roles": ["operator"] }` |
| 프레임 가드(`appliesTo`)가 걸리는 화면 | `{ "required": true }` |
| 로그인·가입·약관·공개 콘텐츠 | `{ "required": false }` |
| 산문/정책서에 권한 서술이 있음 | 그 서술대로 (+`policies`에 `POL.*`) |
| **근거 없음** | **지어내지 않습니다.** `[확인 필요: 이 동작의 권한]`을 산문에 남기고 비웁니다 |

**빈칸을 "인증 불필요"로 채우지 마세요.** 그게 이 필드를 만든 이유입니다 — 안 쓴 것과 "불필요라고 쓴 것"이
구분되지 않으면 운영자 전용이 공개가 됩니다.

**권한은 틀리면 정보가 새는 자리**라 gap-fill 뒤 풀 리뷰에서 **산문·정책서와 대조**해야 합니다.

## ③-1 보여주는데 아무도 안 가져오는 데이터 — 진입 로드 채우기

```
⚠ 보여준다고 했는데 아무 동작도 가져오지 않는 데이터 244건 (화면 15개) — 조회 요구가 빠졌을 수 있다
     · FEAT.support.inquiry.list — inquiry.title, inquiry.status, inquiry.createdAt … (5건)
⚠ 데이터를 보여주는데 **진입 로드가 하나도 없는 화면** 2개 — 조회 요구가 빠졌을 수 있다
     · FEAT.admin.tenantProvision.detail — 보여주는 값 7개, 진입 로드 0건
```

**둘은 다른 것을 봅니다.** 앞은 "이 값을 아무도 안 가져온다", 뒤는 "이 화면에 진입 조회가 아예 없다".
승인·반려·저장 같은 **변경 동작의 응답**이 화면 값을 덮으면 앞은 0이 되지만 뒤는 그대로 잡힙니다 —
실측에서 그 차이가 상세 화면 둘을 살렸습니다(요청서에 조회가 한 줄도 안 나가고 있었습니다).

옛 화면 설계서에는 **"화면에 들어오면 일어나는 일"** 절 자체가 없습니다. 저작 지침에 그 자리가 없었기
때문이고, 그래서 화면이 데이터를 보여준다고 선언해 놓고 **아무도 가져오지 않는** 상태가 흔합니다.
그런 화면은 인터페이스 요청서에 **한 줄도 안 나갑니다.**

화면마다 값의 출처를 판정해 채웁니다(`easyproduct-screen-design`의 "진입 로드 채우기").

| 값이 어디서 오나 | 무엇을 하나 |
|---|---|
| **서버에서 온다** | 산문에 "화면에 들어오면 일어나는 일" 절을 만들고, `io`에 `{id: "IO.<도메인>.<화면>.load", target: "server", receives: [그 값들]}` 추가 |
| **정적 문구 · 앞 화면에서 받은 값 · 화면에서 계산** | `io`에 넣지 않고, **산문에 어디서 오는지 한 줄** 밝힘 |
| **판정이 안 됨** | `[확인 필요: 이 값의 출처]`를 산문에 남김 — 지어내지 않음 |

**`display`를 지우지 마세요.** 진입 로드의 `receives`와 겹쳐 보여도 뜻이 다르고(`display`=보인다,
`receives`=가져온다), **그 차집합이 이 점검의 근거**입니다. 지우면 다음 누락을 못 잡습니다.

이 검사는 **상설**입니다 — 마이그레이션이 끝난 뒤에도 새 화면마다 같은 누락이 반복됩니다.

## ③-1-2 공통 프레임 블록이 없음 — 껍데기 동작 채우기

```
⚠ 공통 프레임 블록이 없는 화면 설계 index 1개 — 껍데기 동작이 빠졌을 수 있다
     · screens/user/screen-design-user-index.md
```

GNB·LNB·상단바에도 **서버와 주고받는 일**이 있습니다 — 세션 조회, 로그아웃, 워크스페이스 전환.
옛 index는 기계 블록 없는 링크 허브였고, 그래서 이 동작들이 **어느 화면에도 속하지 못해 요청서에서
통째로 샜습니다.** 실측 세트에서 요청서 96건에 세션 조회가 없었습니다.

`easyproduct-screen-design`의 **"공통 프레임 블록 채우기"**대로 채웁니다.

1. index 산문의 "공통 UI 정의"를 읽고, 껍데기가 서버와 주고받는 일을 찾습니다.
2. **화면에 잘못 붙어 있는 전역 동작을 회수합니다.** `IO.my.home.logout` 같은 것이 있으면 프레임으로
   옮기고 그 화면 `io`에서 뺍니다. 옮기면 id가 바뀌므로(`IO.user.shell.logout`) 백엔드 계약의 `basis`가
   그 id를 가리키면 함께 고칩니다 — 점검기가 죽은 링크로 잡아 줍니다.
3. **`appliesTo`에 예외 화면을 적습니다.** 로그인 화면을 안 빼면 **"로그인하려면 세션이 있어야 한다"**는
   순환이 문서에 박힙니다.
4. 스키마 사본(`screen-design-frame.v1.schema.json`)을 `screens/<범위>/schemas/`에 복사하고 frontmatter에
   `machine.{tag: screendesign.frame, schema}`를 넣습니다.
5. 요청서를 다시 뽑습니다 — **`--domain frame`이 새로 생깁니다.**

## ③-1-3 프레임 동작 id에 범위가 빠짐 (0.10.0~0.10.1에 만든 프레임)

```
⚠ 소유 프레임과 어긋난 동작 id 2건 — **이관 필요**(앞 두 마디가 소속을 드러내야 한다)
     · IO.frame.shell.session (FRAME.backoffice.shell) → IO.backoffice.shell.<동작>
```

0.10.0의 예시에 `IO.frame.<이름>.*`처럼 **범위가 빠져 있었습니다.** 사용자 앱과 백오피스가 둘 다
껍데기를 `shell`이라 부르면 양쪽이 같은 id가 되어, 요청서·백엔드 `basis`가 엉뚱한 동작에 붙습니다.

앞 두 마디를 소유 프레임의 두 마디로 맞추면 됩니다 — `FRAME.backoffice.shell` → `IO.backoffice.shell.session`.
백엔드 계약의 `basis`가 옛 id를 가리키면 함께 고칩니다(안 고치면 죽은 링크로 잡히니 조용히 새지는 않습니다).
그다음 요청서를 다시 뽑으면 끝입니다.

**범위가 하나뿐인 세트도 고치세요.** 지금은 충돌이 안 나 통과하지만, 백오피스를 추가하는 순간 부딪힙니다.

## ③-2 옛 배치(범위 통짜) 요청서 — 도메인별로 다시 뽑기

```
⚠ 옛 배치(범위 통짜) 인터페이스 요청서 1건 — **다시 뽑기 필요**
   · interface-requests/interface-request-user.md
```

블록에 `domain`이 없거나 `from`의 출처가 여럿이면 옛 배치입니다. 통짜면 **화면 하나만 고쳐도 요청서 전체가
낡음**이 되어 어디가 낡았는지 알 수 없고, 담당 개발자가 갈리는 경계(사용자 앱/백오피스)도 파일에서 안 보입니다.

요청서는 파생물이라 **다시 뽑는 것이 곧 업그레이드**입니다.

```bash
SET=<문서세트>; CHK=<easyproduct-suite>/scripts/check-docs.mjs
mkdir -p "$SET/interface-requests/user/schemas"
cp <스킬>/schemas/interface-request.v1.schema.json "$SET/interface-requests/user/schemas/"
for d in $(node $CHK $SET --emit-interface-request --scope user --list-domains); do
  node $CHK $SET --emit-interface-request --scope user --domain "$d" --transport rest \
    > "$SET/interface-requests/user/interface-request-user-$d.md"
done
```

> **스키마 사본을 옮기는 것이 이 단계의 절반입니다.** 옛 요청서는 세트 루트의 `schemas/`를 썼는데,
> 새 요청서는 **자기 옆 `schemas/`**를 가리킵니다. 안 옮기면 `❌ 스키마 로드 실패`가 나고
> **그 블록의 검사가 통째로 침묵합니다**(죽은 링크·낡음·옛 배치 전부). 점검기가 그 사실을 함께 알려 줍니다.

그다음 **옛 통짜 파일을 지우고**(남겨 두면 같은 요구가 두 곳에 있어 백엔드가 어느 쪽을 볼지 갈립니다)
색인 항목을 새 경로들로 교체합니다. 백엔드 계약의 `basis`는 `IO.*` 앵커를 가리키지 파일을 가리키지 않으므로
손대지 않아도 됩니다.

## ③-3 IA가 한 파일인데 범위가 둘 — 나누기 (선택)

**오류도 경고도 아닙니다.** 한 팀이 다 만드는 제품은 한 파일이 편합니다. 다만 **트랙(브랜치)이 갈렸거나
담당이 다르면** 나누는 편이 낫습니다 — IA만 소유자가 둘이라 문서를 합칠 때마다 충돌합니다.
실측 사례에서 충돌 원인이 **내용이 아니라 frontmatter `revision` 한 줄**이었습니다(본문 1000여 줄은
3-way 머지로 깨끗이 합쳐졌습니다).

```
ssot/ia.md              허브 — 요약·링크만. 기계 블록 없음. machine.includes 로 부분 파일 선언
ssot/ia-user.md         사용자 앱 IA   — 자기 revision + ia.features
ssot/ia-backoffice.md   백오피스 IA    — 자기 revision + ia.features
```

`easyproduct-ia-designer`의 **"범위가 둘인데 한 파일이면 — 나누기"**대로 **옮기기만** 합니다.

| | |
|---|---|
| 가르는 기준 | **`audience` 값**(`user`/`admin`)입니다. 파일명이 아니라 그게 정본입니다 |
| `FEAT` id | **한 글자도 안 바꿉니다.** 화면 설계·시나리오·백엔드가 전부 그 id로 참조합니다 |
| 허브에 남기는 것 | **링크와 요약만.** 화면 지도·네비게이션을 남기면 허브가 다시 공동 편집 파일이 됩니다 |
| 새로 켜지는 검사 | **중복 기능 정의**(오류) · **범위와 어긋난 기능**(경고) |

> **git이 1→2 분리를 추적하지 못합니다.** 여러 브랜치에서 각자 IA를 고치고 있다면 **먼저 합친 뒤에
> 나누세요** — 반대로 하면 다른 브랜치의 수정분이 유실됩니다.

## ③-4 백엔드 계약의 근거·필드 이름 (계약 문서가 있을 때)

```
⚠ 요청서에 없는 동작을 근거로 든 인터페이스 4건 — 요구 → 계약 흐름을 안 탔다
     **화면 설계서를 고치세요** — 그 동작이 `client`/`local`로 적혀 있어 요청서에서 빠졌습니다 (4건)
⚠ 같은 뜻을 다른 이름으로 적은 계약 필드 28건 — **이관 필요**
     enum 26건 · optional 2건
```

**첫 번째는 고칠 자리가 갈립니다.** 점검기가 갈래를 판정해 알려 주니 그대로 따르면 됩니다 —
`client`/`local`이면 **화면 설계서**, `server`인데 안 실렸으면 **요청서 재생성**.
**`ops`로 바꾸지 마세요** — 화면에 있는 동작이면 근거 갈래는 `screen-io`가 맞고, 옮기면 화면이 안 고쳐집니다.

**두 번째는 이름만 바꾸면 됩니다** — 허용값은 `values`, 필수 여부는 `required`.
지금은 경고라 막히지 않지만, 소비자가 표준 이름만 읽으면 **별칭으로 적힌 것은 그 값이 없는 필드로 보입니다.**

## ③-5 목록의 항목 모양 · 값의 근거 갈래 (계약 문서가 있을 때)

```
⚠ 목록인데 항목 모양이 없는 계약 필드 71건
     **형제 필드를 모으세요** — 원소의 필드를 `이름[].속성`으로 펼쳐 적으셨습니다 (38건)
     **원소 모양을 적으세요** — 어디에도 원소 정보가 없습니다 (33건)
⚠ 근거 갈래가 안 적힌 계약 필드 276건 — 저장된 값인지, 파생인지, 일회성인지 모릅니다
```

**첫 번째도 고칠 자리가 갈립니다.** `이름[].속성`으로 펼쳐 적으셨으면 **형제를 `items.fields`로 모으는**
일이고(지어내는 것이 아니라 옮기는 일), 원소 정보가 아예 없으면 새로 적어야 합니다.

**두 번째는 셋 중 하나입니다** — 저장된 값이면 `dataModel`, 계산·가공해 만들면 `derivedFrom`,
저장 안 하면 `transient: true`. **산문에도 근거가 없으면 비워 두세요.** 지어낸 값은 집계에서 사라져
아무도 다시 안 봅니다.

> **기계가 못 잡는 반대편이 더 위험합니다.** `dataModel`이 붙었는데 **사실은 파생**인 것 — 끝 네 자리만
> 남긴 값이 원본 개념에 그대로 걸려 있으면, 저장 설계를 읽는 쪽이 **원본을 저장한다고 오해합니다.**
> 이름이 실재하니 점검기는 통과시킵니다. 이건 풀 리뷰의 **미러 충실도**에서 봅니다.

화면 쪽에는 **`transientReceives`**가 새로 생겼습니다 — 총 건수·다음 페이지 커서처럼 **받지만 저장 안 하는
결과값**의 자리입니다. 예전엔 "산문에만 둔다"고 했는데, 그러면 요청서에 안 나가고 **백엔드는 그 요구가
없는 줄 압니다.**

## ③-6 항목 단위 개정 기록 (계약 문서가 있을 때)

```
⚠ 항목 단위 개정 기록이 없습니다(interface-revisions.json) — 인터페이스 130건
     소비자가 "내가 맞춘 판이 아직 유효한가"를 물을 자리가 없습니다.
     → `--sync-revisions` 를 한 번 돌리면 전부 **개정 1**로 시작합니다.
```

한 번 돌리면 끝입니다. **과거 이력은 지어내지 않습니다** — 몇 번 고쳐졌든 지금을 1세대로 봅니다
(문서 `revision`을 처음 도입했을 때와 같은 규칙).

그 뒤로는 계약이 바뀔 때마다 `--sync-revisions`로 갱신하면 되고, CI에서는 `--check-revisions`로
**갱신을 잊었는지** 잡습니다. 손으로 적을 일은 하나뿐입니다 — **필드는 그대로인데 뜻이 바뀌었을 때**
계약 문서의 `interfaces[].revision`을 올립니다(내리면 오류).

## ③-7 생성기가 자란 뒤로 안 뽑은 요청서

```
⚠ 생성기가 자란 뒤로 다시 안 뽑은 요청서 21건 — 새 칸이 빈 채로 남아 있을 수 있습니다
     · interface-requests/user/interface-request-user-order.md (뽑은 판 표시 없음 → 지금 0.12.2)
     → `--emit-interface-request` 로 다시 뽑으세요. 화면은 그대로라 다른 검사는 아무 말도 하지 않습니다.
```

**요청서는 화면 + 생성기 로직의 함수**인데 신선도 검사는 화면만 봅니다. 화면을 안 고쳤어도 생성기가
새 칸을 실어 나르게 되면 **옛 요청서는 그 칸이 빈 채로** 남습니다 — 그리고 다른 검사는 전부 통과합니다.

다시 뽑기 전에 **스키마 사본부터 갱신**하세요(`schemas/interface-request.v1.schema.json`).
사본이 낡았으면 새 칸이 "스키마에 없는 키"로 걸립니다.

> **요청서에 "개정을 올리세요"라고는 하지 않습니다.** 요청서는 파생물이라 사람이 개정을 매길 자리가
> 없습니다. 대신 **"다시 뽑혀 바뀜 — 하류 재검토 필요"**로 알리니, 바뀐 요구가 **계약에 반영됐는지만**
> 보시면 됩니다.

## ④ 파장 지도 밖 문서 종류 — `derivesFrom`으로 편입

프로젝트 고유 문서(요청서·오픈이슈 목록 등)는 표준 지도에 없어 **상류로도 하류로도 안 잡힙니다.**
색인 항목에 상류를 적어 주면 편입됩니다:

```json
{ "docType": "api-requests", "path": "api-requests/user/api-auth.md", "role": "supporting",
  "derivesFrom": ["screens/user/screen-design-user-index.md", "ssot/data-model.md"] }
```

세트 표준 문서인데 빠졌다면 그건 **스킬 쪽 파장 지도를 고쳐야 하는 문제**입니다(알려 주세요).

## ⑤ 스키마 사본이 다름 — 어느 쪽이 최신인지 확인

문서 옆 `schemas/*.json`은 스킬 자산의 **사본**입니다. 스킬을 업그레이드하면 당연히 달라집니다.
**점검기는 방향을 단정하지 않습니다** — 문서를 옛 스킬로 만들었을 수도, 스킬을 안 올렸을 수도 있으니까요.
보통은 스킬 자산 쪽이 최신이므로 그걸로 덮어씁니다.

## ⑥ 리뷰 산출물이 없음 — 첫 기록 만들기

```
⚠ 리뷰 산출물이 없습니다 — LLM 층(산문·미러 충실도, 파장 확인) 미실행으로 봅니다.
```

`reference/reviews/review-<날짜>.md`를 만듭니다(템플릿: `easyproduct-suite/assets/review-template.md`).
스냅샷 해시는 손으로 만들지 말고 받아 쓰세요:

```bash
node <easyproduct-suite>/scripts/check-docs.mjs <문서세트> --print-snapshot
```

`schemas/review.v1.schema.json` 사본을 세트에 복사하는 것도 잊지 마세요.

## 순서 요약

```
① 색인 재생성          ← 안 하면 나머지 점검이 그 문서들을 아예 못 본다
② revision 채우기
③ 화면 io gap-fill(target·id·op 이관, 가능하면 policies·semantics)
③-0 인증 요건(auth) 채우기       ← 오류다. 안 채우면 점검이 통과 안 된다
③-1 진입 로드 채우기            ← 안 하면 그 화면은 요청서에 0줄이다
③-1-2 공통 프레임 블록 채우기     ← 껍데기 동작(세션 조회·로그아웃)을 회수한다
③-1-3 프레임 동작 id에 범위 넣기  ← 0.10.0~0.10.1에 만든 프레임만
③-2 요청서 도메인별로 다시 뽑기  ← 위를 다 한 뒤에 (그래야 frame 도메인도 나온다)
③-3 IA 범위별로 나누기(선택)     ← 트랙·담당이 갈렸을 때만
③-4 백엔드 계약 근거·필드 이름   ← 계약 문서가 있을 때만
③-5 목록 항목 모양·근거 갈래     ← 계약 문서가 있을 때만
③-6 항목 단위 개정 기록          ← 계약 문서가 있을 때만
③-7 생성기가 자란 뒤 재생성      ← 요청서가 있을 때만
④ 고유 문서 derivesFrom
⑤ 스키마 사본 갱신
⑥ 첫 리뷰 기록 남기기  ← 여기서 신선도 기준선이 생긴다
```

## 마지막으로 — gap-fill은 "구조만 맞춘 것"입니다

필드를 채웠다고 검증이 끝난 게 아닙니다. **채운 뒤 반드시 풀 리뷰를 이어붙이고**, 그 결과를 리뷰
산출물에 남기세요. 기계 점검만 통과한 상태는 **"구조는 맞음, 의미 점검 미실행"**입니다.

## 스킬을 만드는 사람에게

계약을 바꿀 때는 **네 가지를 반드시 함께** 냅니다(`CLAUDE.md` · checker-guide의 베타 머지 게이트):

1. **감지** — suite Step 1 재진입의 "낡은 구조" 트리거에 그 신호 추가
2. **채움** — 해당 스킬 gap-fill 절차에 "없으면 이렇게 채운다"
3. **가시화** — 점검기가 "누락 n건 — 업그레이드 필요"를 집계해 보고
4. **검증** — 도그푸드에 **기존 세트 재진입 경로**를 한 번 걷기

하나라도 빠지면 반쪽 릴리즈입니다. 신규 생성만 걸으면 이 구멍은 **구조적으로 안 보입니다.**
